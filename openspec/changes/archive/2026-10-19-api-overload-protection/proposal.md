# Proposal

## Why

Нагрузочный тест 2026-10-19 (реальная база, 4 процесса API, открытая модель k6) показал, что
API выдерживает 300 запросов/с, а при 325 зависает целиком, вместе с `/health`, и сам
восстанавливается только через ~5 минут после конца нагрузки. Причина — взаимная блокировка
потоков и соединений с БД. Sync-зависимость проверки пользователя занимает соединение, после
чего эндпоинту нужен ещё один поток. Под всплеском все потоки заняты запросами, ждущими
соединение, а соединения — запросами, ждущими поток. Тупик снимает только тайм-аут пула
(30 с), а входящая очередь не ограничена. Короткий всплеск трафика превращается в
многоминутный простой.

## What Changes

- Каждый процесс API обрабатывает одновременно не больше запросов, чем у него соединений с БД
  (по умолчанию 10 при `API_WORKERS=4`). Остальные ждут в очереди процесса.
- Запрос, не дождавшийся обработки за `API_QUEUE_TIMEOUT_SECONDS` (по умолчанию 2 с),
  получает 503 с кодом `OVERLOADED`, `retryable: true` и `Retry-After: 1`. Сервис не копит
  бесконечную очередь, а отклоняет лишнее.
- `/health` не стоит в этой очереди. SSE-стрим освобождает место, как только начался ответ:
  стримы живут минутами и БД читают короткими сессиями.
- Ожидание соединения из пула у API ограничено 5 с вместо 30 с: `DB_POOL_TIMEOUT`
  перекрывает это значение. У воркеров умолчание не меняется (30 с).
- UI повторяет запрос текущего пользователя при ошибке с `retryable: true`. Иначе одна 503
  уводила бы админа со страниц парсинга.
- k6: режим постоянного потока `RATE` (открытая модель) в `scripts/loadtest`.

### Modified Capabilities
- `platform/api-conventions`: перегруженный API отвечает 503 `OVERLOADED`, а не зависает.
- `platform/runtime-config`: `API_QUEUE_TIMEOUT_SECONDS` и `DB_POOL_TIMEOUT` (ожидание
  соединения у API по умолчанию 5 с).

## Impact

- `backend/overload.py` (новый ASGI-middleware), `backend/main.py` (подключение, создание в
  lifespan), `backend/db/session.py` (тайм-аут пула по роли), `backend/settings.py`,
  `backend/errors.py` (код `OVERLOADED`).
- `frontend/src/App.tsx` (повтор `me` при retryable-ошибке).
- `scripts/loadtest/` (режим `RATE`), README, `.env.example`.
- Под перегрузкой клиенты получают 503 вместо долгого ожидания. Повторы retryable-ошибок в
  UI уже есть у запросов TanStack Query по умолчанию.
