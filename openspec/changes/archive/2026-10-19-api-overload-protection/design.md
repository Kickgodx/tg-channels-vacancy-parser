# Design

## Context

У процесса API пул соединений `pool_size + max_overflow` (при `API_WORKERS=4` это 5 + 5),
столько же потоков в threadpool anyio (`api_thread_limit`). Sync-эндпоинт с
`Depends(get_current_user)` проходит через threadpool несколько раз: зависимость
`get_current_user` берёт соединение (сессия `get_db` держит его до конца запроса), затем сам
эндпоинт ждёт свободный поток. uvicorn принимает запросы без ограничения. Exit-код
`get_db` FastAPI выполняет вне лимитера потоков, тупика на выходе нет.

Кто ещё берёт соединения в процессе API: `/health` (своё соединение), короткие сессии SSE
через `run_in_threadpool`, вторая сессия у мутаций с `Idempotency-Key`, лидер (очистка, курсы,
`db_*` при сборе метрик), задачи и recover в режиме `inprocess`.

## Goals / Non-Goals

**Goals:** исключить тупик «поток ↔ соединение» и неограниченную очередь; под перегрузкой
API отвечает быстрым 503, а после неё сразу работает как обычно.

**Non-Goals:** поднять пропускную способность; приоритеты запросов; общий лимит на все
процессы или реплики.

## Decisions

1. **Лимит одновременных запросов = соединений процесса** (`api_thread_limit`). Пока запросов
   в работе не больше, чем потоков, запрос никогда не ждёт поток: каждый занимает не больше
   одного потока за раз. Значит, тупик невозможен. Отдельной настройки нет: размер задают
   `DB_POOL_SIZE` / `DB_MAX_OVERFLOW`, а лимит больше пула вернул бы тупик.
   *Альтернативы:* `uvicorn --limit-concurrency` считает TCP-соединения: keep-alive-клиенты
   без запросов съедают лимит, лишнее отклоняется сразу и без нашего формата ошибки. Перевести
   `get_current_user` в async с одним переходом в поток — большой рефакторинг, и он не
   ограничивает очередь.

2. **Чистый ASGI-middleware с `anyio.Semaphore` и `anyio.move_on_after`.** Ожидание в
   очереди FIFO не дольше `API_QUEUE_TIMEOUT_SECONDS`; не дождался — 503 `OVERLOADED`,
   `retryable: true`, `Retry-After: 1`. Семафор создаётся в lifespan и кладётся в
   `app.state`: так у каждого процесса и у каждого `TestClient` свой. Без lifespan
   middleware ничего не ограничивает. Отмена anyio на семафоре безопасна: разрешение,
   выданное в момент тайм-аута, возвращается.
   *Почему 2 с:* при штатной нагрузке очередь пуста (p99 < 0,1 с). При перегрузке
   обслуженный запрос ждёт не больше 2 с, а лишние получают отказ раньше, чем человек
   нажмёт «обновить».

3. **Место в очереди — самое внутреннее middleware** (добавляется первым). CORS, HTTP-журнал,
   метрики и трассы видят 503: у браузера есть CORS-заголовки, отказы считаются в
   `http_requests_total{status="503"}`. Preflight отвечает CORS и в очередь не попадает.

4. **Исключения.** `/api/v1/health` проходит без очереди: liveness не должен падать из-за
   перегрузки, своё соединение он ждёт не дольше тайм-аута пула. SSE (`text/event-stream`)
   отдаёт место на `http.response.start`: стрим держит соединение HTTP минутами, а БД не
   держит. Экспорт (`StreamingResponse` с открытой сессией) место держит до конца.

5. **`pool_timeout` по роли:** API 5 с, воркеры 30 с, `DB_POOL_TIMEOUT` перекрывает. При
   лимите из п. 1 запрос ждёт соединение, только если в процессе работают фоновые задачи
   или мутация берёт вторую сессию. Это миллисекунды, пока соседний запрос не закончится.
   5 с — страховка от редких циклов, например сразу несколько мутаций, ждущих вторую
   сессию. У воркеров потоки LLM прогона законно ждут соединение для AI-кэша дольше.

## Risks / Trade-offs

- [Под перегрузкой UI видит ошибки] → `retryable: true`; запросы TanStack Query
  повторяются по умолчанию (3 раза с паузой), `me` начинает повторяться в этом изменении.
- [Отказы тоже стоят CPU: журнал, метрики, трассы] → это дешевле обычного запроса. Если
  станет узким местом, исключение отказов из журнала — отдельное изменение.
- [Фоновая работа в `inprocess` может ждать соединение до 5 с] → в `inprocess` пул общий с
  запросами, ожидание — до окончания текущего запроса. Ошибка AI-кэша уже обрабатывается
  как промах.
- [Сокращённый лимит для async-эндпоинтов без БД] → таких в API почти нет (`/health`
  исключён).

## Результат нагрузочного теста

Смесь UI, реальная база, 4 процесса, OTel, постоянный поток k6, по 60 с:

| Поток | До изменения | После |
|---|---|---|
| 300 | 300, p99 0,08 с | 300, p99 0,10 с |
| 325–350 | зависание, `/health` не отвечает ~5 мин | — |
| 400 | — | 400, p99 0,15 с, без ошибок |
| 450 | зависание, 25% ошибок, тайм-ауты 60 с | 444, p99 0,51 с, без ошибок |
| 600 | — | ~430 успешных/с, 24% 503, p99 2,2 с |
| 800 | — | ~400 успешных/с, 46% 503, p99 2,2 с |

После каждой ступени `/health` отвечал за 0,01 с, тайм-аутов пула — ни одного. Закрытая
модель (64 клиента): 545 RPS против 517 до изменения — ограничитель пропускную способность
не снижает.

## Migration Plan

Изменение только в коде и env, без миграций. Откат — откатить коммит. Слишком частые 503 при
штатной нагрузке лечатся увеличением `API_QUEUE_TIMEOUT_SECONDS` или пула
(`DB_POOL_SIZE` / `DB_MAX_OVERFLOW` в пределах `max_connections`).
