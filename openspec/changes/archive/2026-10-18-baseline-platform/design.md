# Design

## Context

Мотивация — в `proposal.md`. Baseline: требования описывают реализованное
поведение, код не меняется. Источники:
- соглашения API — `backend/errors.py`, `backend/http_logging.py`, `backend/main.py`
  (CORS, префикс, обработчики ошибок);
- конфигурация — `backend/settings.py`, `tg_jobs_parser/config/loader.py`,
  `tg_jobs_parser/config/schema.py`, `backend/api/routes/config.py`,
  `backend/api/routes/health.py`;
- обслуживание — `backend/db/migrate.py`, `backend/services/db_cleanup.py`,
  репозитории с `purge_*`, `backend/db/transfer.py`, `tg_jobs_parser/cli/db.py`,
  старт и часовой поток в `backend/main.py`.

Уже зафиксированное не повторяется, на него ссылаются: регистрация и
`JWT_SECRET` (`identity/authentication`), доступ (`identity/access-control`),
снимок конфигурации прогона (`parse-runs`), режимы `rq`/`inprocess` и
идемпотентность (`platform/durable-jobs`), архивирование вакансий
(`catalog/vacancy-retention`), кэш выдачи HH (`sources/hh-sync`), каталог моделей
(`platform/llm-governance`).

## Goals / Non-Goals

**Goals:**
- Формат ошибки и код по статусу — в одном месте; другие спецификации называют
  только код.
- Правила `APP_ENV` — одно требование: новое различие `dev`/`prod` становится
  правкой spec.
- Для каждого сценария — тест или «теста нет».

**Non-Goals:**
- Метрики Prometheus, трассировка, ротация файлов журнала, liveness воркеров —
  эксплуатационная наблюдаемость, не контракт поведения.
- Размер пула соединений по роли процесса — деталь реализации.
- Проверка `X-API-Key`: расхождение этапа 1 (ключ проверяется не на всех роутерах)
  отложено, требование появится вместе с его решением.

## Decisions

### 1. Три спецификации по потребителю

`api-conventions` читает разработчик клиента, `runtime-config` — тот, кто
разворачивает, `data-maintenance` — тот, кто отвечает за данные. Одна
`platform/operations` смешала бы формат ошибок с миграциями.

### 2. Сроки хранения — здесь, а не у владельцев таблиц

Очистка — один проход по многим таблицам с общими правилами (пачки, изоляция
сбоев). Сроки хранения собраны в `platform/data-maintenance`; архив вакансий и кэш
выдачи HH уже описаны у своих владельцев и только упоминаются.

### 3. Расхождения — не в spec

Поведение, похожее на ошибку (список ниже), в требования не включено.

## Risks / Trade-offs

- [Список маскируемых ключей журнала — в spec] → новый вид секрета требует правки
  spec; это осознанно, утечка секрета в журнал — заметное пользователю нарушение.
- [Требование без теста] → помечено в tasks.md.

## Open Questions

Наблюдения, найденные при сборе требований; в spec не закреплены, каждое —
кандидат в отдельное решение:

1. **Опечатка в ключе `config.yaml` молча игнорируется.** Схема не запрещает
   лишние поля: неверно написанная настройка не действует, ошибки нет.
2. **Неизвестное значение `PARSE_JOB_BACKEND`, `LLM_JOB_BACKEND` или
   `HH_SYNC_JOB_BACKEND` молча включает `inprocess`.** Опечатка в `rq` оставляет
   задачи в процессе API без ошибки.
3. **`/health` проверяет только наличие `config.yaml`.** Файл с ошибкой даёт
   `status: ok`, хотя запуск прогона и `/config` падают.
4. **`db import --mode replace` удаляет данные пользователей.** Очистка вакансий
   каскадом удаляет оценки, письма и LLM-задачи всех пользователей, а
   предупреждение говорит только о прогонах, вакансиях, курсах и кэше. Сам дамп
   пользователей, резюме, пресеты и кэш выдачи HH не содержит, так что перенос
   между инстансами их теряет.
5. **Ошибка конфигурации на `/config` — 500 с `retryable: false`, необработанная
   500 — `retryable: true`.** Одинаковый статус по-разному подсказывает клиенту
   повтор.
