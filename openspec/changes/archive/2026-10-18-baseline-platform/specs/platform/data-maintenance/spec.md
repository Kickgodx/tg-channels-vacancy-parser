# Spec Delta

## Purpose

Обслуживание базы: применение миграций, плановая очистка служебных таблиц по
срокам хранения, дамп и импорт общего корпуса между инстансами.

## ADDED Requirements

### Requirement: Схема базы обновляется при старте
API MUST при старте применять все миграции схемы до последней под блокировкой Postgres: несколько процессов, стартующих одновременно, применяют их по очереди, и следующий видит уже готовую схему. Ошибка миграции SHALL останавливать старт, без создания таблиц в обход миграций; блокировка снимается и при ошибке.

#### Scenario: Миграция упала
- **WHEN** миграция завершилась ошибкой
- **THEN** API не стартует, блокировка миграций снята

### Requirement: Плановая очистка при старте и раз в час
При старте API и затем раз в час MUST выполняться очистка: архивирование вакансий (см. `catalog/vacancy-retention`), кэш выдачи HH и грейды HH (см. `sources/hh-sync`), а также служебные таблицы ниже. Сбой очистки SHALL только записываться в журнал и не мешать работе API.

#### Scenario: Сбой очистки
- **WHEN** при старте очистка служебных таблиц упала
- **THEN** API стартует, в журнале предупреждение

### Requirement: Завершённые задачи удаляются по сроку хранения
Завершённые LLM-задачи MUST удаляться через `retention.llm_jobs_ttl_days` (30) суток после завершения, завершённые прогоны и HH sync — через `retention.parse_runs_ttl_days` (180); без времени завершения срок считается от создания. Активные задачи SHALL NOT удаляться. Вакансии, оценки и письма остаются. `0` хранит всегда.

#### Scenario: Старые и свежие задачи
- **WHEN** есть LLM-задачи `done` 40 суток назад, `error` без времени завершения, созданная 40 суток назад, `done` 5 суток назад и `running` 40 суток
- **THEN** удалены первые две, `done` 5 суток и `running` остаются

#### Scenario: Срок 0
- **WHEN** `retention.llm_jobs_ttl_days: 0` и `retention.parse_runs_ttl_days: 0`
- **THEN** задачи и прогоны любого возраста остаются

### Requirement: Ненужные служебные записи удаляются
Очистка MUST удалять просроченные записи AI-кэша и записи другой версии промпта извлечения, истёкшие ключи идемпотентности (ключ живёт 24 часа после ответа, незавершённый — 15 минут) и refresh-токены — истёкшие и отозванные. Ротированный, но не истёкший refresh-токен SHALL оставаться: по нему распознаётся повтор украденного токена.

#### Scenario: AI-кэш
- **WHEN** в кэше записи просроченная, свежая, бессрочная и свежая от прежней версии промпта
- **THEN** остаются свежая и бессрочная

#### Scenario: Refresh-токены
- **WHEN** есть истёкший, отозванный и ротированный живой токены
- **THEN** удалены истёкший и отозванный

### Requirement: Курсы хранятся ограниченно, последние остаются
Курсы MUST удаляться старше `retention.exchange_rates_ttl_days` (60) суток, но не новее окна `fx.sync_days_on_startup`. Последняя дата курсов SHALL оставаться всегда, даже если она старше срока: без неё рублёвые суммы не посчитать. `0` хранит всегда.

#### Scenario: ЦБ давно недоступен
- **WHEN** курсы есть только за 100 и 150 суток назад, срок — 60
- **THEN** удалены курсы 150-дневной давности, курсы 100-дневной остаются

#### Scenario: Окно догрузки длиннее срока
- **WHEN** срок — 60 суток, `fx.sync_days_on_startup: 90`, есть курсы за 0, 80 и 100 суток назад
- **THEN** курсы за 100 суток удалены, за 0 и 80 остаются

### Requirement: Очистка идёт пачками и не падает целиком
Каждая таблица MUST очищаться пачками по 1000 строк в отдельных транзакциях, не больше 50 пачек за проход; остаток SHALL удаляться следующим проходом. Ошибка очистки одной таблицы не останавливает очистку остальных.

#### Scenario: Сбой одной таблицы
- **WHEN** очистка AI-кэша упала с ошибкой базы
- **THEN** старые прогоны всё равно удалены

### Requirement: Дамп и импорт общего корпуса
`cli db dump` MUST сохранять в JSON (`format_version` 1) прогоны, курсы, вакансии, связки прогон–вакансия, появления и AI-кэш. `cli db import` SHALL загружать дамп в режиме `merge` (по умолчанию: вставка с обновлением по первичному ключу) или `replace` (после подтверждения очистить эти таблицы и загрузить заново). Дамп другой версии отклоняется; в дампе без связок или появлений они восстанавливаются из вакансий.

#### Scenario: Перенос с merge
- **WHEN** дамп снят, вакансии и прогоны удалены, дамп импортирован в `merge`
- **THEN** вакансия и её прогон восстановлены, связь вакансии с прогоном сохранена

#### Scenario: replace
- **WHEN** после снятия дампа в базу добавлена вакансия, и дамп импортирован в `replace`
- **THEN** в базе только вакансии из дампа

#### Scenario: Неизвестная версия
- **WHEN** у дампа `format_version` 99
- **THEN** импорт отклоняется с ошибкой версии
