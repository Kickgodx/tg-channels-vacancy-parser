# Spec Delta

## ADDED Requirements

### Requirement: Sync запускается с окном поиска
`POST /hh/sync` MUST принимать окно `all` (по умолчанию), `7d`, `14d`, `30d` (вакансии за последние 7, 14 или 30 дней) или `range` с `date_from` и `date_to` в формате `YYYY-MM-DD`, `date_from` не позже `date_to`; другое окно или неполный `range` — 422. Если HH выключен (`hh.enabled`) или не заданы `HH_API_TOKEN` и `HH_CONTACT_EMAIL`, ответ SHALL быть 503 `UPSTREAM_UNAVAILABLE`, sync не создаётся. Иначе — 202 `{job_id}`.

#### Scenario: Окно 7 дней
- **WHEN** администратор запускает sync с `window: 7d`
- **THEN** ответ 202, поиск в HH идёт за 7 дней, `period` sync и итога — 7

#### Scenario: Диапазон без дат
- **WHEN** администратор запускает sync с `window: range` без `date_from`
- **THEN** ответ 422, sync не создан

#### Scenario: Нет токена HH
- **WHEN** `HH_API_TOKEN` не задан
- **THEN** ответ 503, sync не создан

### Requirement: Поиск в HH ограничен по темпу и глубине
Поиск MUST идти по `hh.search` (текст, профессиональные роли, `per_page` до 100) и окну sync. Запросы к HH SHALL идти не чаще `hh.max_rps` (3) в секунду; ответ 429 повторяется до 5 раз с паузой из `Retry-After`, а без него — 1, 2, 4… с. Выдача читается до конца, но не глубже 2000 вакансий (ограничение HH).

#### Scenario: Выдача больше 2000
- **WHEN** HH нашёл 5000 вакансий, `per_page` 100
- **THEN** sync читает 20 страниц, 2000 вакансий

### Requirement: Мультигородные копии — дубли одной вакансии
Вакансии выдачи с одинаковыми работодателем, названием, требованиями, обязанностями, форматом работы, зарплатой и опытом MUST считаться одной группой; город, адрес, дата и id не учитываются. Канон группы SHALL быть участником, чьи детали уже скачаны, а если таких нет — первым в выдаче. Копии сохраняются как дубли `hh_multicity` со ссылкой на канон и в списке каталога не видны.

#### Scenario: Та же вакансия в двух городах
- **WHEN** в выдаче одна вакансия ACME в Москве и в Казани
- **THEN** одна группа: канон — московская (первая), казанская — дубль `hh_multicity`

#### Scenario: Детали уже есть у копии
- **WHEN** при повторном sync первой в выдаче идёт копия без деталей, а у другого участника детали скачаны
- **THEN** канон — участник со скачанными деталями

### Requirement: Детали вакансии скачиваются один раз
Детали канона MUST запрашиваться, только если они ещё не скачаны или изменилось содержание вакансии в выдаче; иначе используется сохранённая вакансия (`details_skipped`). Копии SHALL сохраняться из короткой выдачи и не затирать уже сохранённую полную карточку. Ошибка HH при деталях не прерывает sync: вакансия сохраняется из короткой выдачи, ошибка — в `errors` итога.

#### Scenario: Повторный sync
- **WHEN** sync повторяется по той же выдаче
- **THEN** детали не запрашиваются, `details_skipped` равен числу групп

#### Scenario: Изменилось содержание
- **WHEN** у вакансии со скачанными деталями в выдаче изменились требования
- **THEN** при этом sync детали запрашиваются заново

#### Scenario: Копия с полной карточкой
- **WHEN** вакансия раньше сохранена с деталями, а теперь стала копией в группе
- **THEN** её сохранённый текст не заменяется короткой выдачей

### Requirement: Вакансия HH сохраняется без LLM
Вакансия HH MUST получать id `sha256(hh:{id})`, канал `hh`, ссылку без служебных параметров HH, дату публикации HH, текст из названия и описания без HTML, зарплату из вилки HH (`RUR` — `RUB`), формат работы (из нескольких — `remote`, затем `hybrid`, затем `office`), `vacancy_score` 100 и источник разбора `hh_api`. Специализации SHALL браться из профессиональных ролей HH, «Тестировщик» добавляет `QA`, «Программист, разработчик» — `Software Engineer`. Повторный sync перезаписывает поля вакансии.

#### Scenario: Детали вакансии
- **WHEN** скачаны детали вакансии с описанием в HTML, вилкой в `RUR` и форматом `REMOTE`
- **THEN** текст без тегов, валюта `RUB`, формат `remote`, источник разбора `hh_api`

#### Scenario: Ссылка со служебным параметром
- **WHEN** ссылка HH содержит `?tech_source=api`
- **THEN** у вакансии ссылка без этого параметра

### Requirement: Грейд вакансии HH — по требуемому опыту
Грейд MUST определяться по опыту HH: без опыта — `intern`, 1–3 года — `junior`, 3–6 лет — `middle`, больше 6 — `senior+`, иначе `unknown`. Вакансиям HH с грейдом `unknown` и сохранённым текстом опыта грейд SHALL проставляться по этому тексту при старте API и раз в час.

#### Scenario: Опыт 3–6 лет
- **WHEN** у вакансии опыт `between3And6`
- **THEN** грейд `middle`

#### Scenario: Старая строка без грейда
- **WHEN** у сохранённой вакансии HH грейд `unknown`, опыт «От 3 до 6 лет»
- **THEN** после очистки при старте грейд `middle`

### Requirement: Вакансии HH записываются пачками
Вакансии sync MUST записываться в базу пачками по `hh.db_flush_batch_size` (30) с фиксацией каждой пачки, в том числе посреди большой группы копий. Записанное до сбоя или отмены SHALL оставаться в базе.

#### Scenario: Пачки
- **WHEN** `hh.db_flush_batch_size: 2`, sync сохраняет пять вакансий
- **THEN** вакансии записаны тремя пачками

### Requirement: Кэш выдачи HH очищается по сроку
После успешного sync, а также при старте API и раз в час, строки кэша выдачи, не встречавшиеся в выдаче `hh.listing_ttl_days` (40) суток, MUST удаляться; для таких вакансий детали скачаются заново. `0` SHALL отключать очистку.

#### Scenario: Давно не встречалась
- **WHEN** вакансия не встречалась в выдаче больше 40 суток
- **THEN** её строка кэша выдачи удалена, сама вакансия остаётся в каталоге

### Requirement: Итог и ошибка sync
Итог sync MUST содержать окно, число найденных, групп, дублей, скачанных и пропущенных деталей, новых и обновлённых вакансий, удалённых строк кэша, страниц, пачек, ошибки деталей и длительность; ход — фазу `search`, `details` (сколько групп из скольких) или `purge`. Ошибка HH API SHALL завершать sync `failed` с `HH API error: HTTP <код>`, прочая — с типом и текстом до 500 символов; итог на момент сбоя сохраняется, следующий sync можно запускать.

#### Scenario: HH ответил 502
- **WHEN** поиск в HH вернул 502
- **THEN** sync `failed`, `error_message` — `HH API error: HTTP 502`, итог с `searched` 0
- **AND** новый sync запускается

### Requirement: Состояние HH доступно администратору
`GET /hh/status` MUST показывать, включён ли HH, заданы ли токен и email (без их значений), срок кэша выдачи, поисковый запрос и роли, а также число строк кэша выдачи всего, со скачанными деталями и без. `GET /hh/sync-jobs` SHALL отдавать последние sync, новые первыми (10, до 100).

#### Scenario: История sync
- **WHEN** администратор запустил два sync
- **THEN** в истории оба, последний — первым
