# Spec Delta

## Purpose

Учётные записи и сессии: регистрация (первый пользователь — администратор), вход
и лимиты попыток, короткий access-токен, refresh-сессия с ротацией, выход и отзыв
сессий, одноразовые тикеты для SSE.

## ADDED Requirements

### Requirement: Первый зарегистрированный пользователь — администратор
Первый пользователь системы MUST получать права администратора и забирать себе строки резюме и пресетов без владельца (оставшиеся от однопользовательской версии). Последующие пользователи SHALL регистрироваться без прав администратора. Проверка «первый ли» MUST быть атомарной относительно параллельных регистраций.

#### Scenario: Первая регистрация
- **WHEN** в системе нет пользователей, и кто-то регистрируется
- **THEN** ответ 201, пользователь — администратор, резюме и пресеты без владельца теперь принадлежат ему

#### Scenario: Вторая регистрация
- **WHEN** администратор уже есть, и регистрируется ещё один пользователь
- **THEN** новый пользователь не администратор и не видит чужих резюме и пресетов

### Requirement: Регистрацию можно закрыть
При `AUTH_REGISTRATION_OPEN=false` регистрация нового пользователя MUST отклоняться с 403, кроме самого первого пользователя. По умолчанию регистрация открыта в `APP_ENV=dev` и закрыта в `APP_ENV=prod`; явное значение переменной SHALL иметь приоритет над умолчанием режима.

#### Scenario: Регистрация закрыта
- **WHEN** регистрация закрыта, администратор уже есть, и регистрируется новый пользователь
- **THEN** ответ 403, пользователь не создаётся

#### Scenario: Первый пользователь при закрытой регистрации
- **WHEN** регистрация закрыта, а пользователей нет
- **THEN** регистрация проходит, пользователь — администратор

### Requirement: Данные для регистрации проверяются
Email при регистрации MUST быть корректным адресом и SHALL приводиться к нижнему регистру; пароль — от 6 до 256 символов. Занятый email MUST давать 409 `EMAIL_TAKEN`, в том числе при одновременной регистрации одного адреса. Вход SHALL принимать и email, заведённые до появления проверки формата.

#### Scenario: Некорректный email
- **WHEN** регистрация с адресом без `@`
- **THEN** ответ 422, пользователь не создаётся

#### Scenario: Гонка регистраций одного email
- **WHEN** два запроса регистрируют один email одновременно
- **THEN** один получает 201, другой — 409 `EMAIL_TAKEN`, а не 500

### Requirement: Вход выдаёт access-токен и refresh-сессию
Успешный вход MUST возвращать короткий access-токен (`JWT_TTL_MINUTES`, по умолчанию 15) и данные пользователя и устанавливать refresh-cookie новой сессии. Неверная пара email–пароль SHALL давать 401, отключённый пользователь — 403. Тот же вход MUST быть доступен формой OAuth2 password (`/auth/token`) для Swagger UI.

#### Scenario: Успешный вход
- **WHEN** пользователь входит с верным email и паролем
- **THEN** ответ содержит `access_token`, `expires_in` и пользователя, установлен refresh-cookie

#### Scenario: Неверный пароль
- **WHEN** пароль неверный
- **THEN** ответ 401, cookie не устанавливается

### Requirement: Попытки входа ограничены
Регистрация, вход и смена пароля MUST учитываться в лимите попыток с одного IP (`AUTH_RATE_LIMIT_PER_MINUTE`, 20 в минуту). Неудачные входы на один email MUST считаться в окне `AUTH_FAILED_LOGIN_WINDOW_SECONDS` (900 с); после `AUTH_MAX_FAILED_LOGINS` (5) вход SHALL отклоняться до проверки пароля. Отказ — 429 `RATE_LIMITED` с `Retry-After`; успешный вход сбрасывает счётчик email.

#### Scenario: Перебор пароля
- **WHEN** на email пришло 5 неудачных входов за окно, и приходит шестой — даже с верным паролем
- **THEN** ответ 429 `RATE_LIMITED` с заголовком `Retry-After`, пароль не проверяется

#### Scenario: Успешный вход сбрасывает счётчик
- **WHEN** после нескольких неудач (меньше лимита) пользователь входит успешно
- **THEN** счётчик неудач по email обнуляется

#### Scenario: Счётчики общие для процессов API
- **WHEN** задан `REDIS_URL`
- **THEN** неудачные входы считаются в Redis, общем для всех процессов API

### Requirement: Access-токен принимается только из заголовка
API MUST принимать access-токен только из заголовка `Authorization: Bearer`; токен в query-параметре SHALL NOT приниматься ни REST-, ни SSE-эндпоинтами. Запрос без действующего токена — 401 `NOT_AUTHENTICATED`. Токен, выпущенный до появления версии токенов, считается версией 0.

#### Scenario: Токен в query
- **WHEN** клиент передаёт действующий токен как `?access_token=`
- **THEN** ответ 401

### Requirement: Refresh-сессия в защищённом cookie
Refresh-токен MUST храниться в httpOnly cookie с `SameSite=Strict` и путём `/api/v1/auth`, с флагом `Secure` в `APP_ENV=prod` (по умолчанию). Срок сессии — `REFRESH_TTL_DAYS` (30) и SHALL продлеваться при каждом обновлении. Refresh-токен в БД хранится только хэшем.

#### Scenario: Cookie при входе
- **WHEN** пользователь входит
- **THEN** ответ ставит cookie `tgjp_refresh` с `HttpOnly`, `SameSite=Strict` и `Path=/api/v1/auth`

### Requirement: Обновление ротирует refresh-токен
`POST /auth/refresh` MUST выдавать новый access-токен и заменять refresh-токен следующим в той же сессии. Нет cookie, токен неизвестен, истёк, отозван или пользователь отключён — 401. Повтор уже ротированного токена в пределах 30 секунд SHALL выдавать access без новой ротации (параллельные вкладки); повтор позже MUST отзывать всю сессию, не затрагивая другие сессии пользователя.

#### Scenario: Обычное обновление
- **WHEN** клиент обновляет access по действующему refresh-cookie
- **THEN** ответ содержит новый access-токен, cookie заменён новым refresh-токеном

#### Scenario: Две вкладки обновились одновременно
- **WHEN** тот же refresh-токен предъявлен второй раз в пределах 30 секунд после ротации
- **THEN** ответ содержит access-токен, сессия не отзывается

#### Scenario: Повтор украденного токена
- **WHEN** ротированный refresh-токен предъявлен позже 30 секунд
- **THEN** ответ 401, вся сессия отозвана, другие сессии пользователя работают

### Requirement: Выход и отзыв сессий
`POST /auth/logout` MUST отзывать текущую refresh-сессию и стирать cookie; без cookie SHALL отвечать 204. `POST /auth/logout-all` и смена пароля MUST отзывать все access-токены и refresh-сессии пользователя (через версию токенов). Смена пароля требует текущий пароль: неверный — 400 и учитывается как неудачный вход; после смены выдаётся новая сессия.

#### Scenario: Выход везде
- **WHEN** пользователь вызывает «выйти везде»
- **THEN** прежние access-токены дают 401, прежние refresh-cookie не обновляются

#### Scenario: Смена пароля
- **WHEN** пользователь меняет пароль, указав верный текущий
- **THEN** старые токены и сессии отозваны, ответ содержит новый access-токен и cookie новой сессии

### Requirement: SSE получает доступ одноразовым тикетом
`POST /auth/sse-ticket` MUST выдавать вошедшему пользователю тикет на 30 секунд, принимаемый SSE-эндпоинтами в `?ticket=`. Тикет SHALL приниматься один раз (в том числе между процессами API при заданном `REDIS_URL`), SHALL NOT заменять access-токен и обратно, и MUST отзываться вместе с версией токенов пользователя. Тикет маскируется в логах HTTP.

#### Scenario: Повторное использование тикета
- **WHEN** тикет уже предъявлен SSE-эндпоинту и предъявляется снова
- **THEN** ответ 401

#### Scenario: Тикет вместо access-токена
- **WHEN** тикет передан в `Authorization: Bearer` REST-эндпоинта
- **THEN** ответ 401

### Requirement: Секрет подписи обязателен в prod
В `APP_ENV=prod` backend MUST отказываться стартовать без `JWT_SECRET` длиной от 32 символов. В `APP_ENV=dev` без секрета SHALL использоваться временный секрет процесса, и сессии сбрасываются при рестарте.

#### Scenario: prod без секрета
- **WHEN** backend стартует в `APP_ENV=prod` с `JWT_SECRET` короче 32 символов
- **THEN** старт прерывается ошибкой конфигурации, значение секрета в сообщение не попадает
