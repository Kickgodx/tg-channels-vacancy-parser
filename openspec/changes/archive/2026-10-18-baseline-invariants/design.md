# Design

## Context

Мотивация — в `proposal.md`. Это baseline: требования описывают уже реализованное
поведение, код не меняется. Источники — код (`backend/api/deps.py`,
`backend/api/routes/{auth,runs,hh,llm_jobs,resumes,filters,vacancies}.py`,
`backend/services/{auth_service,auth_rate_limit,sse_tickets,idempotency,run_service,llm_job_service,hh_sync_job_service}.py`,
`backend/db/*_job_repository.py`, `parse_run_repository.py`, `backend/workers/recover*.py`),
тесты и README. Уже зафиксированные в `openspec/specs/` требования (LLM в `primary`,
отмена импорта и HH sync, кэш оценок и писем) не повторяются.

## Goals / Non-Goals

**Goals:**
- Требования, которые подтверждаются кодом и тестами, — с числами по умолчанию,
  кодами ошибок и именами переменных окружения, как в коде.
- Для каждого сценария — тест или явная пометка «теста нет» (tasks.md).

**Non-Goals:**
- Изменение поведения, в том числе там, где найдено расхождение (ниже).
- Формат ошибок, SSE (ping, fallback на опрос БД), dev/prod-проверки адреса —
  `platform/api-conventions` и `platform/runtime-config`, этап 5.
- Чекпоинты каналов и чтение Telegram — `ingestion/telegram-fetch`, этап 2.
- Квоты и бюджеты LLM — `platform/llm-governance`, этап 3.

## Decisions

### 1. Общий контракт — в `platform/durable-jobs`, частные — в своих спецификациях

Lease, попытки, recover, флаг отмены, единственность, `Idempotency-Key` и
`rq`/`inprocess` описаны один раз для всех трёх типов задач. Где задача
останавливается при отмене (между текстами, страницами, после ответа модели) —
в спецификациях прогона, импорта, HH и LLM-задач. Так правка контракта не
расходится по трём местам.

Альтернатива — описать контракт в каждой спецификации: отвергнута, именно так
расходились три реализации (разные словари статусов, ветки recover).

### 2. Права — по видам данных, а не по списку эндпоинтов

`identity/access-control` называет группы (общие данные, админские операции,
личные данные) и примеры эндпоинтов, а не полный перечень маршрутов. Полный
перечень проверяется тестом `tests/test_api_access.py`, который параметризован
списками путей — он и есть исполняемая форма требования.

### 3. Числа по умолчанию — в требованиях, где на них опирается поведение

Лимиты входа (20/мин, 5 неудач за 900 с), TTL access (15 мин), refresh (30 дней),
окно повторной ротации (30 с), TTL SSE-тикета (30 с), лимиты попыток (3/2/2),
`EXPORT_MAX_ROWS` (50 000) записаны рядом с именем переменной. Каждое число —
в одном требовании.

## Risks / Trade-offs

- [Baseline закрепляет поведение, которое может оказаться ошибкой] → найденные
  расхождения не записаны в требования (ниже), их решают отдельные изменения.
- [Требование без теста] → помечено в tasks.md; добавление теста — отдельная задача
  вне baseline.

## Open Questions

Расхождения, найденные при сборе требований. В spec они не закреплены; каждое —
кандидат в отдельное изменение:

1. **`API_KEY` проверяется не везде.** README: «если задан — заголовок `X-API-Key`
   для API». Роутеры `/resumes`, `/filters`, `/llm-jobs` его не проверяют (остальные —
   проверяют). Сейчас требование про `API_KEY` в spec не включено.
2. **`Idempotency-Key` прогона общий для всех администраторов.** У HH sync и импорта
   ключ привязан к пользователю (`user:<id>`), у прогона — к общему `api`: два
   администратора с одинаковым ключом получат один ответ. В spec записан только
   общий для всех трёх контракт повтора.
3. **Отмена завершённого прогона — 404.** У LLM-задач и HH sync такая отмена
   возвращает 200 с текущим состоянием (изменение F). В spec для прогона записаны
   только `queued` и `running`.
