# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/career/*`. Текущее устройство:

- `vacancy_matches` и `cover_letters` — PK `(resume_id, vacancy_id)`, колонка
  `model` = фактически ответившая модель (`usage.model`, может быть fallback).
  Upsert — `user_content_repository.upsert_vacancy_match` / `upsert_cover_letter`.
- `POST /resumes/{id}/match/{vacancy_id}` и `.../cover-letter/...`
  (`backend/api/routes/resumes.py`): без `force` при наличии строки → 200 из БД,
  иначе — `llm_job_runner.enqueue` → 202. Тон письма приходит в теле, в ключ
  кэша не входит.
- Модель выбирает `OpenRouterClient` из `AiConfig`:
  `resolved_match_model()` (`match_model` → `model`) и
  `resolved_cover_letter_model()` (`cover_letter_model` → матчинга); fallback —
  `resolved_fallback_models()`. Работа идёт в LLM-воркере (`match_service`,
  `cover_letter_service`), конфиг читается там же через `load_config`.
- `MATCH_PROMPT_VERSION` / `COVER_LETTER_PROMPT_VERSION` объявлены в
  `tg_jobs_parser/ai/prompts.py` и нигде не используются.
- Ответы: `_match_to_out` / `_letter_to_out` в `resumes.py` — их же использует
  `llm_jobs._job_to_out` для итога задачи. Список вакансий (`vacancy_repository`,
  выборка `select(VacancyRow, VacancyMatchRow, preview)` с outer join по
  `resume_id`) уже получает строку оценки целиком.
- UI (`VacancyModal.tsx`) при существующем результате всегда шлёт `force=true`;
  без `force` — только когда результата нет.

## Goals / Non-Goals

**Goals:**
- Одна функция определяет актуальность оценки и письма — её используют и
  решение «200 или 202», и все ответы с `stale`.
- Существующие данные после миграции ведут себя предсказуемо, без массового
  «всё устарело».

**Non-Goals:**
- Хранение нескольких результатов на пару (история по моделям) — вариант B
  отвергнут.
- Автоматический пересчёт устаревших результатов в фоне или массово.
- Учёт `extra_notes` письма и связи «письмо устарело, потому что пересчитали
  оценку» — не в этом изменении.
- Изменение колонки Match, сортировки и фильтров списка.

## Decisions

### 1. Две новые колонки, а не смена PK

В `vacancy_matches` и `cover_letters` — `requested_model VARCHAR(128) NULL` и
`prompt_version VARCHAR(32) NULL` (миграция `030_llm_results_requested_model`).
PK не меняется — одна строка на пару (вариант A). `model` остаётся фактической
моделью и по-прежнему показывается в UI.

Альтернатива — одна колонка-отпечаток (hash модели и версии): отвергнута, по
отдельным колонкам видно, *что* устарело, и это проще отлаживать.

### 2. Что записывать и когда

Запрошенная модель и версия берутся в воркере в момент вызова LLM из того же
`AiConfig`, по которому `OpenRouterClient` выбирает модель:
`cfg.ai.resolved_match_model()` / `resolved_cover_letter_model()` и константы
версий. Не в момент `POST`: если конфиг сменился, пока задача ждала в очереди,
в строку попадёт то, с чем модель реально спрашивали.

### 3. Одна функция актуальности

Новый модуль `backend/services/llm_result_freshness.py`:
`match_is_stale(row, ai)` и `cover_letter_is_stale(row, ai)`. Правило:
запрошенная модель = `row.requested_model or row.model`; устарело, если она ≠
текущей настроенной или `row.prompt_version` не пуст и ≠ текущей константе.
Пустая версия (строки до миграции) по версии не устаревает (спеки, требования
про строки до учёта). Тон письма в «устарело» не входит — его сравнивает только
`POST` (решение 4), потому что `GET` тон не передаёт.

### 4. Решение «200 или 202» в роутах

`POST` оценки: 200 из БД, только если строка есть и не устарела, иначе
`enqueue` (с `force=False` в параметрах задачи — она всё равно перезапишет
строку). `POST` письма: 200, только если строка есть, не устарела и
`row.tone == запрошенному тону`. Активная задача той же пары по-прежнему
переиспользуется `enqueue` — повторный клик не плодит задачи.

### 5. Признак `stale` в ответах

- `VacancyMatchOut.stale`, `CoverLetterOut.stale` — считаются в `_match_to_out` /
  `_letter_to_out` (им передаётся текущий `AiConfig`); итог LLM-задачи получает
  их автоматически.
- Элемент списка: `VacancyListItem.match_stale: bool | None` (None — оценки нет).
  Репозиторий списка получает текущую конфигурацию матчинга параметром от роута
  и вызывает `match_is_stale` для строки оценки — без SQL-веток и без чтения
  конфига в репозитории.
- Frontend: поля в `types/api.ts`; в `VacancyModal.tsx` у оценки и письма с
  `stale` — подпись «получено другой моделью или версией промпта — переоцените /
  перегенерируйте». Начальная оценка из элемента списка несёт `match_stale`.

### 6. Миграция существующих строк

`requested_model = model`, `prompt_version` остаётся NULL. Следствия: строка,
полученная текущей основной моделью, — актуальна; полученная fallback-моделью
или прежней моделью — устарела (честно: её делала не та модель, что настроена).
Массовой пометки из-за неизвестной версии нет.

## Risks / Trade-offs

- [Строки, сделанные fallback-моделью до миграции, станут `stale`] → это
  правда о них; пересчёт — по клику, массового пересчёта нет.
- [Bump версии промпта помечает устаревшими все оценки/письма с этой версией] →
  ожидаемо по правилу «смысловое изменение промпта → bump»; LLM вызывается
  только по запросу пользователя, расход не взлетает.
- [Конфиг читается на каждый ответ со `stale`] → `load_config` кэширован по
  mtime файла, лишнего I/O нет.
- [Смена тона без `force` теперь тратит вызов LLM и квоту] → это и есть
  запрошенное поведение; UI и раньше слал `force` при перегенерации.

## Migration Plan

Миграция `030` применяется при старте backend (`upgrade head`), обратима
(`downgrade` удаляет колонки). Откат кода без отката миграции безопасен: старый
код новые nullable-колонки не читает.
