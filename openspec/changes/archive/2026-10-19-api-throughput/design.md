# Design

## Context

Замеры 2026-10-19. Копия базы, отдельный контейнер на образе backend, настройки как
в compose (`APP_ENV=dev`, OTel включён, один процесс uvicorn). Нагрузка — k6 в той же
Docker-сети, профили — `py-spy record --gil`, планы — `EXPLAIN ANALYZE`. Машина одна,
16 vCPU делят API, Postgres и k6: цифры годятся для сравнения вариантов.

| Сценарий (RPS) | 1.8 тыс. вакансий | 45 тыс. вакансий |
|---|---|---|
| `/auth/me` | ~350 | — |
| список, стр. 1 | 115–140 | ~155 |
| поиск `q=` | ~70 | 4.6 (p99 22 с) |
| метрики / зарплаты без кэша | — | 73 / 56 |
| смесь UI | ~140 | ~40 |

Что показали профили и планы:
- API занимает ~120% CPU, Postgres — 7–15%: упирается один процесс под GIL.
  Плато наступает уже при 1–16 параллельных клиентах.
- `ORDER BY ts_rank(to_tsvector('russian', cleaned_text), …)` пересчитывает
  tsvector для каждого совпадения. GIN-индекс `ix_vacancies_fts` ускоряет только
  `WHERE`. 45 тыс. вакансий, `q=python` (15.8 тыс. совпадений): 1408 мс.
  С хранимой колонкой — 238 мс, ранжирование 1000 свежих совпадений — 41 мс,
  сортировка по дате — 3 мс.
- Список в dev: ~30% CPU — `render_body` разбирает весь ответ (68 КБ),
  маскирует и сериализует обратно, хотя в журнал уходит 4 КБ.
- `/auth/me`: ~20% — переходы в threadpool, ~28% — starlette/fastapi, ~25% —
  ORM-загрузка `UserRow`. Синхронные `verify_api_key` и `bearer_token` не делают
  I/O, но каждая занимает поток.
- Список: 24% — 50 моделей `VacancyListItem`, 13% — разбор строк psycopg, ORM —
  identity map и состояние сущностей.
- Метрики — 8 SQL подряд, зарплатная аналитика — 10.
- 4 процесса дают ×2.7, 8 — ×3.6. При 8 процессах с пулом 20+20 у каждого
  `max_connections=100` кончились (`too many clients`).
- Go-прототип с тем же SQL и проверкой JWT: список 2 255 RPS на ядро, потолок
  ~3.7 тыс. RPS — Postgres занимает 7.5 ядра. Смена стека — не цель этого
  изменения.

Что в коде сейчас:
- `backend.main.main()` вызывает `uvicorn.run(app, …)` объектом: так модуль не
  импортируется дважды, но несколько воркеров требуют строку импорта.
- Lifespan в каждом процессе выполняет миграции, очистку, синхронизацию курсов,
  поднимает поток TTL и сервер `/metrics`.
- Лимиты `/auth` и одноразовость SSE-тикетов уже в Redis при `REDIS_URL`.
  Без JWT_SECRET в dev секрет временный, свой у каждого процесса.
- `_DBPoolCollector` и `_DBStatsCollector` — custom collectors глобального
  `REGISTRY`; gauge'и созданы без `multiprocess_mode`.

Решения пользователя (2026-10-19), все по рекомендованным вариантам:
- ранжирование — среди 1000 совпадений окна;
- текущий пользователь — без кэша, только лёгкий запрос;
- `API_WORKERS`, в compose 4;
- нагрузочные инструменты в репозитории: k6, HTML-отчёт, Prometheus и Grafana.

## Goals / Non-Goals

**Goals:**
- Поиск не деградирует с ростом корпуса: стоимость ранжирования ограничена окном.
- API использует больше одного ядра в контейнере, не превышая общий лимит
  соединений с БД.
- Ответы API байт-в-байт прежние, кроме порядка выдачи с `q` за окном.
- Нагрузочный тест воспроизводится одной командой из `scripts/loadtest/`.

**Non-Goals:**
- Отказ от `pool_pre_ping`. Он даёт один round-trip на запрос, но без него
  первый запрос на каждом соединении после рестарта Postgres падает 500.
  `pool_recycle` этот случай не закрывает. Вклад в замерах — единицы процентов.
- Async SQLAlchemy/asyncpg, смена стека, кэш страниц списка, реплики для чтения.
- Кэш пользователя при проверке токена: отзыв токенов должен работать сразу.
- Изменение умолчаний `APP_ENV` и `OTEL_TRACES_SAMPLE_RATIO`. Это выбор
  развёртывания, он описывается в документации.

## Decisions

### 1. `search_tsv` — generated stored column

`search_tsv tsvector GENERATED ALWAYS AS (to_tsvector('russian', cleaned_text))
STORED` и GIN `ix_vacancies_search_tsv`. Индекс `ix_vacancies_fts` удаляется:
выражение больше нигде не используется. В модели колонка объявлена через
`Computed(persisted=True)` и `deferred`: ORM её не пишет и не читает по умолчанию.

Код, перебирающий `VacancyRow.__table__.columns`, пропускает computed-колонки:
- dict для upsert (`upsert_vacancies`);
- дамп и импорт (`backend/db/transfer.py`);
- Core-выборка списка.

Без этого INSERT упадёт на записи в generated-колонку.

`fts_query(document, q)` принимает колонку-документ (`c.search_tsv`) вместо
текста. Альтернатива — триггер вместо generated: лишний код без выигрыша,
Postgres 16 поддерживает stored generated.

### 2. Ранжирование только в окне 1000

Константа `FTS_RANK_WINDOW = 1000` в `vacancy_repository`. При `q` порядок такой:

```
ORDER BY
  CASE WHEN id IN (<первые 1000 id под фильтрами по выбранной сортировке>)
       THEN ts_rank(search_tsv, tsq) END DESC NULLS LAST,
  <выбранная сортировка>, id
```

Подзапрос окна строится теми же фильтрами и той же сортировкой; для `match_score`
— с тем же join на `vacancy_matches`. `CASE` вычисляется лениво: `ts_rank`
считается только для 1000 строк. Порядок общий для списка и экспорта: оба берут
`_vacancy_order_by`. В списке вакансий прогона нет фильтра `q`, и `ts_rank` там
не нужен: условие `q` из `_vacancy_order_by` для него не применяется.

Альтернативы:
- полный `ts_rank` по хранимой колонке — 238 мс на 45 тыс. и рост с корпусом;
- только дата — теряется релевантность;
- RUM-индекс — расширения нет в `postgres:16-alpine`.

**Страница — в два запроса, когда нужна полная сортировка.** Выявлено при
итоговом замере: с окном ранжирование стоило 15 мс, а запрос — 560 мс. Postgres
строил превью (`substr(cleaned_text)` с чтением из TOAST) для всех 15.8 тыс.
совпадений до сортировки. При `q` или сортировке не по `post_date desc` (индекс
`ix_vacancies_active_post_date` не работает) список сначала выбирает `id` страницы
узким запросом, затем колонки и превью для этих `id`, порядок восстанавливается в
Python (`_fetch_page`). Список без `q` по дате, с фильтрами или без, остаётся одним
запросом по индексу.

### 3. HTTP-журнал: одна запись и дешёвое тело

`HttpLoggingMiddleware` пишет одну запись `RESPONSE METHOD path status Nms {json}`.
В JSON добавляется `request` с полями `client`, `headers`, `body`. Префикс
`RESPONSE` сохраняется, чтобы LogQL из README продолжал работать.

Тело копится не больше чем `HTTP_LOG_BODY_LIMIT` + 1 байт, полный размер
считается отдельно. Целиком (`json.loads` → `redact`) разбирается только тело не
длиннее лимита. Длиннее — регулярное маскирование пар `"ключ": "строка"` и
маскирование незакрытой строки после чувствительного ключа в конце среза.

Альтернатива — оставить две записи и только удешевить тело. Но запись запроса до
обработки — это вторая сериализация заголовков и вторая строка в Loki на каждый
запрос, а начало долгих запросов видно в трассах.

### 4. Меньше работы на запрос

- `verify_api_key`, `bearer_token`, `sse_credentials` → `async def`: FastAPI
  вызывает их в event loop без threadpool.
- `get_current_user` возвращает `CurrentUser` (frozen dataclass: `id`, `email`,
  `is_admin`, `is_active`, `token_version`, `created_at`) из одного Core-запроса
  по первичному ключу. Проверка версии токена и активности — как сейчас.
  `require_admin` и все роуты принимают `CurrentUser`. Смена пароля и прочие
  мутации загружают `UserRow` явно через `db.get`.
- Список: `select(<колонки без raw_text, cleaned_text, search_tsv>, preview)`
  вместо ORM-сущности. `row_to_list_item` читает атрибуты `Row` так же, как
  атрибуты сущности.
- Метрики: один запрос с `GROUPING SETS ((detected_grade), (work_format), ())` даёт
  total, число с зарплатой, распределения по грейду и формату и зарплату по
  грейду. Второй — специализации: число и средняя зарплата через тот же lateral,
  топы и границы отбираются в Python, при равенстве — по названию. Отдельно
  остаются дневные бакеты и курс. Итого 8 запросов агрегатов → 3.
- Зарплатная аналитика (10 → 5):
  - квантили по грейду и формату — один `GROUPING SETS`;
  - помесячно и по годам — один;
  - четыре разреза «период × группа» — один;
  - специализации и распределение остаются отдельными.

  Ordered-set агрегаты (`percentile_cont`) поддерживают `GROUPING SETS`.
  Ответы сверены со старой реализацией на рабочей базе (6 наборов фильтров).
  Различия только в составе топов при равном числе — старый SQL сортировал
  только по числу, порядок равных там был случайным.

### 5. Несколько процессов API

- `Settings.api_workers` (`API_WORKERS`, ≥1, по умолчанию 1).
  `check_api_workers(settings)` вызывается в `main()` и в lifespan, но не в
  валидаторе `Settings`. Воркеры RQ читают тот же `.env`, и `API_WORKERS` из
  него не должен ронять llm-worker с `PARSE_JOB_BACKEND=inprocess`.
- `main()` при `api_workers > 1` готовит каталог multiprocess-метрик (очищает,
  ставит `PROMETHEUS_MULTIPROC_DIR` в окружение) и вызывает
  `uvicorn.run("backend.main:app", workers=N)`. Supervisor uvicorn перезапускает
  упавший воркер. При N = 1 — прежний вызов объектом.
- Пул: `pool_limits` для роли `api` делит размер и overflow на N (не меньше 1).
  Lifespan ставит `total_tokens` anyio-лимитера threadpool равным
  `size + overflow` процесса. Так потоков не больше, чем соединений, — тот же
  инвариант, что сейчас (40 = 20 + 20).
- Лидер процесса (`backend/leader.py`): отдельное соединение без пула и
  `pg_try_advisory_lock(<ключ лидера API>)`. В lifespan — одна попытка
  синхронно: при успехе стартовая очистка выполняется до «Backend готов», как
  сейчас. Иначе — фоновый поток с попыткой раз в 30 с.

  Лидер выполняет:
  - стартовую и ежечасную очистку;
  - синхронизацию курсов при старте;
  - сервер `/metrics`;
  - сбор файлов умерших процессов (`mark_process_dead` для pid, которых нет).

  Потеря соединения снимает лидерство: обязанности останавливаются, поток
  возвращается к попыткам. Advisory lock работает и между контейнерами — второй
  контейнер API не повторит очистку.
- Метрики: gauge'и API получают `multiprocess_mode` (`livesum` для текущих
  значений, `max` для меток времени). Сервер лидера при multiprocess отдаёт
  `CollectorRegistry` с `MultiProcessCollector` и `_DBStatsCollector`. Пул БД в
  multiprocess публикуют gauge'и `livesum`, которые каждый процесс обновляет
  потоком раз в 10 с, вместо `_DBPoolCollector`. В одном процессе всё как сейчас.
- Recover-циклы `inprocess` остаются в каждом процессе: при N > 1 `inprocess`
  запрещён (см. spec).

### 6. Нагрузочные инструменты

`scripts/loadtest/`:
- `k6/catalog.js` — сценарии из замеров (`me`, список, фильтры, поиск, карточка,
  агрегаты с кэшем и без, смесь, логин) в одном файле с выбором через `EP`;
- `clone_db.sh` — копия базы в `tgjobs_lt` и множитель корпуса;
- `run.sh` — запуск k6 в Docker-сети compose;
- `README.md` — порядок работы и предупреждение не грузить рабочую базу.

Отчёт: `K6_WEB_DASHBOARD=true`, `K6_WEB_DASHBOARD_EXPORT` → `report.html`.
Prometheus получает флаг `--web.enable-remote-write-receiver` (порт уже на
loopback). k6 пишет туда `-o experimental-prometheus-rw` при `PROM_RW=1`. Дашборд
`k6.json`: RPS, p95/p99, ошибки, VU, а рядом — RPS и задержки backend из
instrumentator.

## Risks / Trade-offs

- [Порядок выдачи с `q` меняется за окном] → окно 1000 больше 10 страниц по 50 и
  больше типичного числа совпадений одного запроса на текущем корпусе.
  Требование и сценарий — в spec.
- [Миграция переписывает `vacancies` под ACCESS EXCLUSIVE] → на 1.8 тыс. строк
  меньше секунды. На 45 тыс. — секунды; старт API и так ждёт миграции.
- [Регулярное маскирование обрезанного тела слабее разбора JSON] → чувствительные
  тела (вход, регистрация, смена пароля) короче лимита и разбираются целиком.
  Незакрытое значение на границе маскируется. Есть тест.
- [Файлы multiprocess-метрик умерших процессов] → лидер вызывает
  `mark_process_dead`. Каталог очищается при старте контейнера.
- [Стартовая очистка не на лидере] → в одном процессе лидер берётся синхронно,
  поведение не меняется. При N процессах её выполняет первый взявший lock.
- [Кэши COUNT и агрегатов — свои в каждом процессе] → отставание уже ограничено
  `ANALYTICS_CACHE_SECONDS` для записей другим процессом (`catalog/analytics`).
- [Remote write receiver принимает запись без аутентификации] → порт Prometheus
  опубликован только на `INFRA_BIND_ADDR` (loopback); в README отмечено.

## Migration Plan

1. Миграция `search_tsv` применяется при старте backend, как все.
2. `API_WORKERS: 4` в compose. Откат — `API_WORKERS=1` в `.env`, код работает
   в обоих режимах.
3. Откат миграции — `downgrade` возвращает `ix_vacancies_fts` и удаляет колонку.
