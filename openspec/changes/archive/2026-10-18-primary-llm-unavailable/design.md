# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Текущее устройство,
от которого отталкивается решение:

- `run_parse` (`tg_jobs_parser/parse_runner.py`) создаёт `AIEnrichmentService`
  до запуска фоновой вычитки каналов (`fetch.start()`); при исключении пишет
  предупреждение «AI не запущен» в `parse_warnings` и продолжает без LLM —
  одинаково в `assist` и `primary`. Конструктор парсера Telethon в сеть не ходит.
- `run_parse_job` (`backend/workers/parse_tasks.py`) любое исключение из
  `run_parse` переводит в `failed` с `error_message = str(e)`; `failed`
  терминален, recover его не трогает.
- `AIEnrichmentService.enrich` проверяет `ai.max_posts_per_run` **до** обращения
  к кэшу и при достижении потолка возвращает вакансию с полями правил в обоих
  режимах; счётчик `stats.calls` увеличивается позже, отдельно от проверки.
- `partial` выставляется по `incomplete_reason` из `run_parse`: сейчас — при
  `rate_limit_skipped` вне `assist` и при доле ошибок выше `max_error_ratio`.
  Чекпоинты по ходу прогона двигаются, пока `_llm_posts_lost` ложно.
- `run_import_job` (`backend/services/import_service.py`) при сбое конструктора
  `AIEnrichmentService` ставит предупреждение и разбирает тексты правилами.
  Любое исключение из него `llm_tasks.run_llm_job` переводит в `error` с
  `error_message`; итог по уже обработанным текстам уже записан в `result`.
- UI показывает `error_message` прогона и задачи импорта — менять его не нужно.

## Goals / Non-Goals

**Goals:**
- Отказ запуска LLM в `primary` виден сразу и однозначно, без побочных записей.
- Поведение при потолке вызовов в `primary` совпадает с поведением при
  отключении LLM (квота, circuit breaker): пост потерян → `partial`, чекпоинты
  стоят.

**Non-Goals:**
- Предпроверка LLM в API при `POST /runs` (ошибка ещё до постановки в очередь).
  Окружение API и воркера может различаться, поэтому окончательная проверка всё
  равно в воркере; предпроверку можно добавить отдельно как улучшение UX.
- Изменение `assist` при сбое запуска LLM и отката импорта на правила при
  исчерпанной квоте или выключенном AI (`ai.enabled: false`, пока задача ждала).
- Новые статусы или поля в API.

## Decisions

### 1. Сбой запуска LLM в primary — исключение из `run_parse` до вычитки

В ветке обработки исключения конструктора `AIEnrichmentService` при
`ai.mode == "primary"` бросать новое `LlmUnavailableError(RuntimeError)`
(объявить рядом с `AIEnrichmentService`), с текстом вида: «LLM не запущен: <причина>.
Режим ai.mode=primary требует LLM — исправьте конфигурацию LLM (ключ, модель)
или запустите прогон без AI либо в режиме assist.» Вычитка ещё не стартовала,
поэтому Telegram не затрагивается. Дальше всё делает существующий обработчик
`run_parse_job`: `failed`, `error_message`, без повторной попытки.

Альтернативы:
- `partial` — отвергнуто: `partial` означает «часть сделана», а здесь не
  разобрано ничего, и прогон зря прочитал бы все каналы.
- Особый код ошибки / статус — отвергнуто: `failed` + текст достаточно, UI и
  API уже это показывают; новый статус затронул бы фронтенд и аналитику прогонов.
- Проверять в `parse_tasks` до вызова `run_parse` — отвергнуто: конфигурация
  LLM и создание сервиса живут в ядре, дублировать их в воркере незачем.

### 2. Потолок проверяется после кэша и вместе с резервированием вызова

В `enrich` порядок становится: порог score → кэш → (отключён ли LLM) →
потолок → вызов. Проверка потолка и `stats.calls += 1` выполняются одной
секцией под `stats._lock`: сейчас между ними окно, и при `ai.concurrency > 1`
потоки могут превысить потолок. При достижении потолка: `skipped_limit += 1`;
`assist` возвращает вакансию с полями правил (как сейчас), `primary` — `None`.
В кэш при этом ничего не пишется (пишется только ответ модели).

Альтернатива — оставить проверку до кэша, а в `primary` просто отбрасывать
пост: отвергнуто, тогда повторный прогон после `partial` упирался бы в потолок
на уже оплаченных постах и не дочитывал бы остаток.

### 3. Потерянный из-за потолка пост учитывается как потеря LLM

- `_llm_posts_lost`: в `primary` истинно и при `stats.skipped_limit > 0` — с
  этого момента `checkpoint_sink` больше не двигает чекпоинты.
- `incomplete_reason` в `run_parse`: после проверки `rate_limit_skipped` и до
  проверки доли ошибок — если `primary` и `skipped_limit > 0`: «AI: достигнут
  лимит ai.max_posts_per_run=N; в режиме primary не разобрано постов: K. Они не
  кэшируются — повторный прогон обработает их.» Берётся первая найденная
  причина (как сейчас между квотой и долей ошибок).
- Финализация `partial` уже не сохраняет чекпоинты — менять не нужно.

### 4. Импорт: сбой запуска LLM — исключение, потолок — свой статус текста

- `run_import_job`: при сбое конструктора `AIEnrichmentService` (ветка
  `config.ai.enabled`) бросать `LlmUnavailableError` с причиной вместо
  предупреждения и отката. Квота списывается только перед вызовом модели по
  каждому тексту — до неё дело не доходит, списаний нет. Уже записанный
  `result` не трогается.
- `_enrich_status`: учитывать прирост `stats.skipped_limit` — при `None`
  возвращать `("error", "Достигнут лимит вызовов LLM (ai.max_posts_per_run) — текст не разобран")`.
  В `assist` такой текст, как и сейчас, сохраняется правилами с предупреждением
  в итоге текста.

## Risks / Trade-offs

- [Прогоны в `primary`, которые раньше «успешно» шли на правилах при сломанной
  конфигурации LLM, теперь падают] → это и есть цель; текст ошибки говорит, что
  исправить, а `assist` / выключенный AI остаются рабочими вариантами.
- [В `primary` при потолке меньше числа новых постов за прогон остаток копится
  от прогона к прогону] → каждый прогон продвигается (кэш потолок не расходует),
  статус `partial` и текст причины делают отставание видимым; в `config.md`
  указать, что потолок в `primary` — ограничитель расходов, а не режим работы.
- [Изменение порядка кэш/потолок меняет `assist`: после потолка пост из кэша
  получит поля LLM, а не правил] → это улучшение (ответ уже оплачен);
  зафиксировано отдельным требованием в `ingestion/ai-extraction`.
- [Задача импорта, упавшая на запуске LLM, после исправления конфигурации
  сама не перезапускается] → пользователь повторяет импорт; уже сохранённые
  тексты вернутся как `exists`, LLM для них не вызывается.

## Migration Plan

Миграций нет. Выкатка — обычный деплой (`docker compose up --build`), откат —
revert коммита. Перед выкаткой стоит проверить, что у прод-конфига в `primary`
LLM запускается (иначе прогоны начнут падать `failed` — что и требуется, но
лучше узнать это до планового запуска).
