# Proposal

## Why

В режиме `ai.mode: primary` LLM — основной источник полей вакансии, правила
по замыслу ему не доверяются (дают ложные специализации, не знают грейд и
период зарплаты). Но есть два пути, где `primary` молча сохраняет вакансии на
одних правилах и двигает чекпоинты каналов, так что эти посты больше никто не
перечитает:

- LLM не стартовал (`AIEnrichmentService` не создался: нет ключа, неизвестная
  модель, не подключён кэш) — прогон идёт целиком на правилах и получает
  `completed` с предупреждением, которое легко не заметить;
- исчерпан потолок `ai.max_posts_per_run` — посты сверх него сохраняются с
  полями правил и не считаются потерянными.

Ручной импорт с LLM при сбое запуска LLM ведёт себя так же: тексты
сохраняются правилами, без проверки «это вакансия?», в общую базу. Именно так
проявлялся недавно исправленный баг с незарегистрированным кэшем в
`llm-worker` — его долго не замечали.

## What Changes

- **BREAKING (поведение):** прогон парсинга в `primary`, у которого не
  запустился LLM, завершается `failed` до чтения Telegram. `error_message`
  называет причину и что сделать (исправить конфигурацию LLM, запустить без AI
  или в `assist`). Вакансии не пишутся, чекпоинты не двигаются, повторной
  попытки нет — причина детерминированная.
- В `primary` пост сверх `ai.max_posts_per_run` не сохраняется (как пост,
  пропущенный из-за отключения LLM): прогон получает `partial` с причиной,
  чекпоинты каналов с первого такого поста не двигаются. Посты не кэшируются —
  следующий прогон разберёт их (ответы из кэша потолок не расходуют).
- Потолок `ai.max_posts_per_run` ограничивает только вызовы LLM: ответ из кэша
  используется и после потолка, в обоих режимах. Сейчас потолок проверяется
  раньше кэша, и после него не используются даже готовые ответы — тогда
  повторный прогон в `primary` не мог бы дочитать пропущенное.
- **BREAKING (поведение):** импорт-задача с LLM (`llm_jobs kind=import`), у
  которой не запустился LLM, завершается `error` с причиной вместо разбора
  правилами. Уже обработанные тексты (ретрай после падения воркера) остаются в
  `result`.
- В импорте пост, не разобранный из-за `ai.max_posts_per_run` в `primary`,
  получает статус `error` с понятным сообщением о лимите, а не общее «Ошибка
  LLM-разбора».
- Без изменений: `assist` (сбой запуска LLM — разбор правилами с
  предупреждением, `completed`); откат импорта на правила при исчерпанной
  суточной квоте пользователя; прогоны и импорт с `ai.enabled: false`.

## Capabilities

### New Capabilities

- `parse-runs`: жизненный цикл прогона парсинга — здесь требования к итоговому
  статусу прогона, когда LLM в `primary` недоступен (не запустился или
  исчерпан потолок вызовов), и к чекпоинтам в этих случаях.
- `ingestion/ai-extraction`: LLM-разбор постов и его режимы — здесь требования,
  что в `primary` пост без ответа LLM не сохраняется с полями правил и что
  потолок вызовов не отменяет ответы из кэша.
- `sources/manual-import`: ручной импорт текста — здесь требование к итогу
  импорт-задачи при сбое запуска LLM и при исчерпании потолка вызовов.

### Modified Capabilities

(нет — спецификаций в `openspec/specs/` пока нет)

## Impact

- Код: `tg_jobs_parser/parse_runner.py` (сбой запуска LLM в `primary`, причина
  `partial` для потолка), `tg_jobs_parser/ai/enricher.py` (потолок в
  `primary`), `backend/services/import_service.py` (сбой запуска LLM → ошибка
  задачи, сообщение для потолка). `backend/workers/parse_tasks.py` и
  `backend/workers/llm_tasks.py` уже переводят исключение в `failed` / `error`
  — менять не нужно.
- API и UI: контракт не меняется — те же статусы (`failed`, `partial`, `error`)
  и `error_message`, которые UI уже показывает.
- Документация: `config.md` (таблица режимов, `max_posts_per_run`), README
  (самовосстановление джоб, импорт).
- Миграций и новых зависимостей нет.
