# Spec Delta

## ADDED Requirements

### Requirement: Итоговую оценку считает система, а не модель
Модель MUST возвращать только оценки 0–100 по измерениям, уверенность, совпавшие и недостающие навыки, сильные стороны, риски и объяснение. `overall_score` SHALL вычисляться системой как взвешенная сумма — роль 0,30, навыки 0,35, уровень 0,20, домен 0,10, формат работы 0,05 — с округлением до целого, половина — к чётному. Число итоговой оценки из ответа модели не используется.

#### Scenario: Взвешенная сумма
- **WHEN** модель оценила роль 90, навыки 75, уровень 85, домен 70, формат 100 и не назвала критичных пробелов
- **THEN** `overall_score` равен 82

#### Scenario: Половина округляется к чётному
- **WHEN** взвешенная сумма равна 82,5, критичных пробелов нет
- **THEN** `overall_score` равен 82

### Requirement: Критичные пробелы ограничивают итоговую оценку
Если среди недостающих навыков есть один с важностью `critical`, `overall_score` MUST быть не выше 69, если два и больше — не выше 59. Потолок SHALL NOT повышать оценку, которая и так ниже. Недостающие навыки важности `important` и `secondary` оценку не ограничивают.

#### Scenario: Один критичный пробел
- **WHEN** взвешенная сумма — 96, и модель назвала один недостающий навык `critical`
- **THEN** `overall_score` равен 69

#### Scenario: Два критичных пробела при низкой оценке
- **WHEN** взвешенная сумма — 17, и модель назвала два недостающих навыка `critical`
- **THEN** `overall_score` равен 17

### Requirement: Ответ модели нормализуется
Оценки и уверенность MUST приводиться к целым 0–100 (дробные и строковые значения округляются, неразбираемые — 0, пропущенное измерение — 0). Важность навыка SHALL сводиться к `critical`, `important` или `secondary` по синонимам (`required`, `must_have` → `critical`; `nice_to_have` → `secondary`; неизвестная → `important`); навык строкой — `important`. Навыков сохраняется не больше 8, сильных сторон и рисков — не больше 5.

#### Scenario: Небрежный ответ
- **WHEN** модель вернула уверенность `"85.7"`, навыки строками, важность `must_have` и шесть сильных сторон
- **THEN** уверенность 86, навыки-строки — `important`, `must_have` — `critical`, сильных сторон 5

### Requirement: Битый ответ модели запрашивается повторно один раз
Если ответ модели на оценку не разбирается как JSON нужной формы, MUST выполняться один повторный запрос той же модели. Вторая неудача SHALL считаться ошибкой модели (дальше — запасные модели, см. `ingestion/ai-extraction`).

#### Scenario: Невалидный JSON
- **WHEN** первый ответ модели — невалидный JSON, второй — корректный
- **THEN** оценка сохраняется по второму ответу, запросов к модели два

### Requirement: Оценку делает модель матчинга
Оценка MUST запрашиваться у `ai.match_model`, а если она пуста — у `ai.model`; режим рассуждений задают `ai.match_reasoning_enabled` и `ai.match_reasoning_effort`. Текст резюме и вакансии SHALL обрезаться до `ai.max_input_chars` каждый.

#### Scenario: Модель матчинга не задана
- **WHEN** `ai.match_model` пуст, `ai.model` — `parse/model`
- **THEN** оценка запрашивается у `parse/model`

### Requirement: Отказ модели завершает задачу оценки ошибкой
Если модель матчинга и запасные модели не дали ответа, задача оценки MUST завершаться `error` с текстом причины в `error_message`; сохранённая оценка пары SHALL NOT меняться.

#### Scenario: Провайдер вернул 503
- **WHEN** вызов модели при оценке завершился ошибкой `OpenRouter API: 503`
- **THEN** задача в статусе `error`, `error_message` содержит `OpenRouter`

### Requirement: Оценка пары требует существующих резюме и вакансии
Запрос оценки MUST давать 404, если вакансии нет; `GET` оценки — 404, если оценка пары ещё не считалась. Ни в одном из этих случаев LLM не вызывается. Чужое резюме — по `identity/access-control`.

#### Scenario: Несуществующая вакансия
- **WHEN** пользователь запрашивает оценку своего резюме по несуществующей вакансии
- **THEN** ответ 404, LLM не вызывается

#### Scenario: Оценки ещё нет
- **WHEN** пользователь запрашивает `GET` оценки пары, которую не оценивал
- **THEN** ответ 404

### Requirement: Список вакансий с резюме показывает оценку пары
Список вакансий с `resume_id` своего резюме MUST содержать у каждой вакансии сохранённую оценку пары (`match_score`, `match_explanation`) или пустые поля, если пару не оценивали. Сортировка `sort_by=match_score` SHALL идти по оценке в направлении `sort_order` (по умолчанию по убыванию), неоценённые вакансии — в конце при любом направлении. Изменённая оценка видна в списке сразу.

#### Scenario: Сортировка по оценке
- **WHEN** из трёх вакансий оценены две — на 88 и 40, и пользователь сортирует по оценке
- **THEN** порядок: 88, 40, неоценённая; у неоценённой `match_score` пуст
