# Design

## Context

Мотивация — в `proposal.md`. Baseline: требования описывают реализованное
поведение, код не меняется. Источники:
- чтение — `tg_jobs_parser/parsers/telegram_telethon.py`, `parse_runner.py`,
  `utils/dates.py`;
- правила — `extraction/vacancy_detector.py`, `extraction/salary_period.py`,
  `extraction/salary_extractor.py`, `extraction/grade_extractor.py`,
  `filters/vacancy_filters.py`, `ingestion/{rules,process,policy}.py`;
- дедуп — `deduplication/deduplicator.py`, `utils/hashing.py`,
  `backend/db/vacancy_repository.py` (`upsert_vacancies`, `_insert_sightings`,
  `archive_expired_vacancies`);
- LLM — `ai/enricher.py`, `ai/merger.py`, `ai/cache.py`, `ai/clients/openrouter.py`.

Уже зафиксированное (LLM в `primary` и потолок вызовов, условия `partial`
прогона, вакансии прогона) не повторяется — на него ссылаются.

## Goals / Non-Goals

**Goals:**
- Правила извлечения — на двух уровнях: результат («резюме получает 0»,
  «годовая сумма делится на 12») и устойчивые эвристики, заметные пользователю
  (веса оценки, пороги, порядок грейдов, пороги годовой зарплаты). Каждое число —
  в одном требовании.
- Для каждого сценария — тест или «теста нет».

**Non-Goals:**
- Словари специализаций, технологий, форматов, исключающих слов и регулярные
  выражения — только ссылкой на модули.
- Перевод зарплаты в рубли и почасовой ставки в месячную — `catalog/salary-fx`,
  этап 4.
- Разбор HH (`hh/mapper`) — `sources/hh-sync`, этап 4.
- Промпт извлечения и golden-набор — `platform/llm-governance` (версии промптов),
  этап 3.

## Decisions

### 1. Разбор правилами и пост-фильтры — одна спецификация

Оценка поста, извлечение полей и пост-фильтры прогона живут вместе в
`ingestion/rule-extraction`: пороги оценки применяются как пост-фильтр, и
разделение по двум спецификациям разорвало бы одно правило отбора.

### 2. Срок жизни вакансии — в `catalog/`, а не в `ingestion/`

Архив по TTL и возврат из архива видны в каталоге (список, `include_archived`) и
касаются всех источников, включая HH. Поэтому `catalog/vacancy-retention`;
сброс архива при повторной публикации тоже там, хотя срабатывает при сохранении.

### 3. Слияние полей LLM — в `ingestion/ai-extraction`

Таблица `assist`/`primary` из `config.md` переложена в два требования. Ссылка
на условия `partial` ведёт в `parse-runs`, чтобы не повторять их.

## Risks / Trade-offs

- [Эвристики оценки и пороги станут частью спецификации] → правка весов или
  порогов теперь — изменение spec; словари остаются вне spec, их правка — нет.
- [Требование без теста] → помечено в tasks.md.

## Open Questions

Наблюдения, найденные при сборе требований; в spec не закреплены, каждое —
кандидат в отдельное решение:

1. **`filters.any_specialization` не снимает фильтр специализаций.** Пост-фильтр
   смотрит только на `filters.specializations`; флаг влияет лишь на контекст
   промпта LLM. UI при «любой роли» шлёт пустой список, поэтому через интерфейс
   всё работает, но запрос API с флагом и непустым списком фильтрует.
2. **Порог `vacancy_score_threshold` действует и с LLM.** В прогоне Telegram пост
   с низкой оценкой правил отбрасывается пост-фильтром даже после того, как LLM
   признал его вакансией (`skip_if_vacancy_score_below` по умолчанию 0, то есть
   LLM вызывается и платится зря). Записано как текущее поведение.
3. **Слишком длинное окно обрезается с конца.** Сохраняется `date_from`, а
   последние, самые свежие дни выпадают.
4. **Лимит `max_posts_per_channel` виден только в логе.** В отличие от FloodWait и
   ошибок чтения, в `parse_warnings` о нём ничего нет, хотя канал прочитан не
   полностью.
