# Design

## Где разделяются роль и технология

Одна функция `split_specializations(specs, techs)` в `tg_jobs_parser/config/schema.py`,
вызываемая в каждой точке входа специализаций: правила (`ingestion/rules.py`), ответ
LLM (`VacancyAIExtraction`, model-validator — закрывает и кэш прежних версий), HH
(`hh/mapper.py`), `FiltersConfig`, `VacancyQuery`. Технология — имя из
`DEFAULT_TECHNOLOGIES`, `_EXTRA_TECHNOLOGY_NAMES` (узнаются только в специализациях:
`C`, `Unity`, `Godot`… — для поиска по тексту слишком шумные) или `TECHNOLOGY_ALIASES`;
составное имя («C#/.NET») — если технологии все части; «<tech> developer / разработчик /
программист» и «программист <tech>» — технология плюс признак роли разработчика.
`model_copy` валидаторы не вызывает, поэтому мёрж LLM канонизирует технологии сам.

Словарь технологий открытый: неизвестное имя сохраняется как есть, канонизируются
только известные алиасы и регистр.

## Логика фильтров

Специализации — «любая из», технологии — «любая из», между группами — «и». Выбрано
пользователем: «Automation QA + Python» должно давать AQA на Python, а не все
Python-вакансии. `any_specialization` снимает только фильтр ролей.

## Существующие вакансии

Миграция 037 переносит технологии из специализаций без LLM (Python-проход по строкам,
словари заморожены копией в миграции). У вакансий, где специализацией был только язык,
роли не остаётся — её по тексту назначает LLM: джоба `reextract` по образцу `import`
(те же lease, recover, отмена, квота по элементам, итог в `llm_jobs.result`). Цели
фиксируются при постановке (до 500), одна активная джоба на всех; ответ «не вакансия»
строку не удаляет. Fallback-роль в миграции (Software Engineer / Backend) отвергнут:
для Python и C++ он часто неверен.

## Фасет технологий

`GET /vacancies/technologies` считает технологии под фильтрами без собственного выбора
технологий — иначе выбранная технология оставляла бы в вариантах только себя и
соседей. Кэш — тот же `cached_aggregate`, что у метрик.
