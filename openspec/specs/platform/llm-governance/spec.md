# platform/llm-governance Specification

## Purpose
Ограничения и учёт расхода LLM для всех его потребителей (парсинг, импорт, оценка,
письма): квота пользователя, суточный бюджет и темп запросов к провайдеру, реакция
на лимит провайдера, каталог моделей и стоимость, версии промптов и golden-набор.

## Requirements

### Requirement: Суточная квота LLM-вызовов пользователя
Пользователь без прав администратора MUST тратить не больше `LLM_USER_DAILY_CALLS` (100) вызовов LLM за UTC-сутки; `0` отключает квоту, администратор ей не ограничен. Оценка и письмо SHALL списывать один вызов при постановке задачи, импорт — по текстам (см. `sources/manual-import`). Ответ из сохранённого результата и возврат уже активной задачи квоту не тратят.

#### Scenario: Квота пользователя
- **WHEN** `LLM_USER_DAILY_CALLS: 2`, и пользователь без прав администратора запрашивает оценку трёх разных пар
- **THEN** первые две задачи поставлены, третий запрос получает отказ по квоте

#### Scenario: Сохранённая оценка при исчерпанной квоте
- **WHEN** квота пользователя исчерпана, и он запрашивает уже оценённую свежую пару
- **THEN** ответ 200 с сохранённой оценкой

#### Scenario: Администратор
- **WHEN** `LLM_USER_DAILY_CALLS: 1`, и администратор запрашивает оценку трёх пар
- **THEN** все три задачи поставлены

### Requirement: Отказ по квоте не создаёт задачу и не ретраится
Запрос сверх квоты MUST получать 429 с кодом `LLM_QUOTA_EXCEEDED` и `retryable: false`; задача SHALL NOT создаваться. Списание MUST быть атомарным: параллельные запросы не превышают квоту, а отказ ничего не списывает. Счётчик каждого пользователя и каждых суток свой.

#### Scenario: Ответ при исчерпанной квоте
- **WHEN** пользователь исчерпал квоту и запрашивает оценку новой пары
- **THEN** ответ 429, `code` — `LLM_QUOTA_EXCEEDED`, `retryable` — `false`

#### Scenario: Списание сверх остатка
- **WHEN** при квоте 3 у пользователя списано 3 вызова, и запрашивается ещё один
- **THEN** отказ, счётчик пользователя остаётся 3; у другого пользователя и в следующие сутки счётчик отдельный

### Requirement: Суточный бюджет пользовательского LLM
Оценки и письма всех пользователей вместе MUST делать не больше `ai.interactive_daily_request_budget` запросов к провайдеру за UTC-сутки; `0` (по умолчанию) — без бюджета. Парсинг SHALL NOT ограничиваться этим бюджетом. Исчерпанный бюджет отключает LLM оценок и писем до полуночи UTC, после неё LLM снова доступен без рестарта.

#### Scenario: Бюджет исчерпан
- **WHEN** бюджет — 2 запроса, и уже сделано 2
- **THEN** следующий запрос к провайдеру не отправляется, LLM оценок и писем отключён до полуночи UTC

#### Scenario: Полночь прошла
- **WHEN** LLM отключён по бюджету, и наступили новые UTC-сутки
- **THEN** следующий запрос к провайдеру отправляется

#### Scenario: Парсинг
- **WHEN** задан бюджет пользовательского LLM
- **THEN** LLM-разбор прогона им не ограничен

### Requirement: Бюджет общий для всех процессов
Счётчик суточного бюджета MUST быть общим для API и всех воркеров через Redis, когда задан `REDIS_URL`. Без Redis или при его недоступности бюджет SHALL считаться внутри процесса, а запрос не блокироваться из-за сбоя хранилища.

#### Scenario: Две реплики
- **WHEN** бюджет — 2, и два процесса с одним Redis запрашивают по очереди
- **THEN** третий запрос в те же сутки отклоняется

#### Scenario: Redis недоступен
- **WHEN** Redis отвечает ошибкой, бюджет — 2
- **THEN** два запроса процесса проходят, третий отклоняется

### Requirement: Темп запросов к провайдеру общий для всех процессов
Запросы к провайдеру MUST идти не чаще `ai.requests_per_minute` (12): внутри процесса — с интервалом не меньше 60 / RPM секунд, а при заданном `REDIS_URL` — ещё и в пределах общего счётчика на минутное окно для API и всех воркеров. Процесс без свободного слота SHALL ждать следующего окна; если Redis недоступен, действует только лимит процесса.

#### Scenario: Две реплики делят темп
- **WHEN** RPM — 3, и два процесса с одним Redis делают по три запроса в одну минуту
- **THEN** сразу проходят три запроса, остальные ждут следующей минуты

#### Scenario: Ожидание слота при отключённом LLM
- **WHEN** процесс ждёт общий слот, а LLM за это время отключился
- **THEN** ожидание прерывается, запрос не отправляется

### Requirement: Исчерпанный лимит провайдера отключает LLM до сброса
Ответ 429 с `X-RateLimit-Remaining: 0` или дневным лимитом MUST при `ai.stop_llm_when_rate_limited` (включено) отключать LLM без повторов: в прогоне — до его конца, у оценок и писем — до времени сброса из `X-RateLimit-Reset`, после которого LLM снова доступен. Иной 429 SHALL повторяться до `ai.max_retries_on_429` (0) раз с паузой до сброса или `ai.retry_base_delay_seconds`, не дольше 120 с.

#### Scenario: Remaining 0
- **WHEN** провайдер ответил 429 с `X-RateLimit-Remaining: 0`
- **THEN** LLM отключается, следующий запрос не отправляется

#### Scenario: Время сброса прошло
- **WHEN** LLM оценок и писем отключён по лимиту провайдера, и время `X-RateLimit-Reset` прошло
- **THEN** следующий запрос отправляется

### Requirement: Модели выбираются из каталога
Модели и их цены MUST браться из `llm_models.yaml` (`LLM_MODELS_PATH`, иначе рядом с `config.yaml`, иначе в корне проекта). Пустая `ai.model` SHALL заменяться `default_model` каталога, пустые `ai.fallback_models` — `default_fallbacks` без основной модели. `ai.model`, а также заданные `ai.fallback_models`, `ai.match_model` и `ai.cover_letter_model` вне каталога — ошибка загрузки конфигурации, которая называет поле и модель. Каталог доступен через `GET /config/llm-models`.

#### Scenario: Конфигурация проекта
- **WHEN** загружается `config.yaml` проекта
- **THEN** каталог конфигурации совпадает с `llm_models.yaml`, все модели конфигурации входят в него

#### Scenario: Модель вне каталога
- **WHEN** `ai.model` — id, которого нет в `llm_models.yaml`
- **THEN** конфигурация не загружается, ошибка называет модель

#### Scenario: Модель матчинга вне каталога
- **WHEN** `ai.model` есть в каталоге, а `ai.match_model` — id, которого в каталоге нет
- **THEN** конфигурация не загружается, ошибка называет `ai.match_model` и эту модель

#### Scenario: Запасная модель вне каталога
- **WHEN** в `ai.fallback_models` одна модель из каталога и одна вне его
- **THEN** конфигурация не загружается, ошибка называет `ai.fallback_models` и модель вне каталога

### Requirement: Стоимость LLM считается по ценам каталога
Стоимость MUST считаться по каждой модели отдельно: токены запроса и ответа, умноженные на цены каталога в USD за миллион токенов. Токены модели без цены SHALL учитываться отдельно (`unpriced_tokens_in`, `unpriced_tokens_out`) и в стоимость не входят. Итоги LLM-статистики прогона MUST содержать `cost_usd_input`, `cost_usd_output` и `cost_usd_total`.

#### Scenario: Две модели в прогоне
- **WHEN** модель A (1 / 2 USD) получила 1 млн входных токенов, модель B (0,5 / 0,5 USD) отдала 2 млн выходных
- **THEN** стоимость входа 1 USD, выхода 1 USD, всего 2 USD

### Requirement: Версия промпта задаётся константой кода
Версии промптов извлечения, оценки и писем MUST задаваться константами кода (`EXTRACT_PROMPT_VERSION`, `MATCH_PROMPT_VERSION`, `COVER_LETTER_PROMPT_VERSION`); их смена инвалидирует кэш извлечения (`ingestion/ai-extraction`) и делает старые оценки и письма устаревшими (`career/*`). Отличающаяся `ai.prompt_version` в конфигурации SHALL давать предупреждение, а кэш ключуется константой.

#### Scenario: Версия в конфигурации отличается
- **WHEN** `ai.prompt_version` в конфигурации не совпадает с `EXTRACT_PROMPT_VERSION`
- **THEN** выдаётся предупреждение, используется `EXTRACT_PROMPT_VERSION`

### Requirement: Golden-набор извлечения проверяется без сети
Golden-набор извлечения MUST содержать не меньше 15 кейсов с уникальными id, и для каждого — сохранённый ответ модели. Проверка без LLM SHALL требовать доли точных совпадений и средней точности полей не ниже 0,8. Живая проверка на модели запускается только явно.

#### Scenario: Офлайн-проверка
- **WHEN** запускается обычный набор тестов
- **THEN** все golden-кейсы оцениваются по сохранённым ответам, обе метрики не ниже 0,8

### Requirement: Вызов квоты возвращается, если модель не ответила
Вызов, списанный при постановке оценки или письма, MUST возвращаться в квоту тех UTC-суток, в которые списан, если задача завершилась `error` или `cancelled` до ответа модели: отмена в очереди или до начала работы, удалены резюме или вакансия, LLM отключён бюджетом или лимитом провайдера, модель не ответила после повторов, сбой постановки, зависшая задача. Отмена после ответа модели SHALL NOT возвращать вызов. Вызов возвращается не больше одного раза.

#### Scenario: Отмена в очереди
- **WHEN** у пользователя списан 1 вызов за задачу оценки, и он отменяет её в очереди
- **THEN** счётчик вызовов пользователя за эти сутки — 0

#### Scenario: Модель не ответила
- **WHEN** задача письма завершилась `error`, потому что модель и запасные модели вернули 503
- **THEN** вызов возвращён в квоту

#### Scenario: Отмена после ответа
- **WHEN** модель ответила, а задача отменена до сохранения результата
- **THEN** задача `cancelled`, вызов не возвращается

#### Scenario: Возврат в сутки списания
- **WHEN** вызов списан 18 октября, а задача завершилась ошибкой уже 19-го
- **THEN** счётчик за 18 октября уменьшился на 1, счётчик за 19-е не изменился

### Requirement: Исчерпанный бюджет отклоняет запрос сразу
Если суточный бюджет пользовательского LLM (`ai.interactive_daily_request_budget`) на сегодня исчерпан, запрос новой оценки или письма MUST получать 429 `LLM_QUOTA_EXCEEDED` с `retryable: false` и сообщением об общем бюджете до полуночи UTC. Задача SHALL NOT создаваться, квота пользователя не списывается. Ответ из сохранённого результата и возврат уже активной задачи бюджет не проверяют.

#### Scenario: Бюджет исчерпан
- **WHEN** бюджет — 2 запроса, оба сделаны, и пользователь запрашивает оценку новой пары
- **THEN** ответ 429 `LLM_QUOTA_EXCEEDED`, задача не создана, счётчик квоты пользователя не изменился

#### Scenario: Сохранённая оценка
- **WHEN** бюджет исчерпан, и пользователь запрашивает уже оценённую свежую пару
- **THEN** ответ 200 с сохранённой оценкой
