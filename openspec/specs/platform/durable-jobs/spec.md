# platform/durable-jobs Specification

## Purpose
Общий контракт фоновых задач — прогона парсинга, LLM-задачи (оценка, письмо,
импорт) и HH sync: постановка, выполнение под lease, восстановление после сбоев,
отмена, единственность активной задачи и идемпотентная постановка.

## Requirements

### Requirement: Статус задачи хранится в Postgres
Статус, прогресс и итог фоновой задачи MUST храниться в Postgres; очередь (Redis) SHALL быть только транспортом. Задача создаётся в статусе `queued` и проходит `queued → running → терминальный`. Терминальные статусы: прогон — `completed`, `partial`, `failed`, `cancelled`; LLM-задача — `done`, `error`, `cancelled`; HH sync — `completed`, `failed`, `cancelled`.

#### Scenario: Постановка задачи
- **WHEN** администратор запускает прогон
- **THEN** ответ 202 с id прогона в статусе `queued`, строка прогона уже есть в БД

#### Scenario: Очередь недоступна при постановке
- **WHEN** задача создана, но поставить её в очередь не удалось
- **THEN** задача сразу получает терминальный статус ошибки (`failed` / `error`) с сообщением о сбое постановки

### Requirement: Задачу выполняет один воркер под lease
Воркер MUST брать задачу атомарным переходом `queued → running` с записью владельца lease и срока lease; одну задачу SHALL получать только один воркер. Каждый такой захват MUST увеличивать счётчик попыток `attempts`. Пока задача выполняется, воркер продлевает lease.

#### Scenario: Два воркера берут одну задачу
- **WHEN** два воркера одновременно пытаются взять одну задачу в `queued`
- **THEN** задачу получает ровно один из них, второй её не выполняет

#### Scenario: Захват увеличивает попытки
- **WHEN** воркер берёт задачу
- **THEN** её `attempts` увеличивается на 1

### Requirement: Итог пишет только владелец lease
Запись прогресса и терминального статуса MUST выполняться только тем воркером, которому принадлежит текущий lease. Воркер, потерявший lease, SHALL прекратить работу и не перезаписывать статус и итог задачи.

#### Scenario: Воркер потерял lease
- **WHEN** lease задачи истёк и задачу перехватило восстановление, а прежний воркер пытается записать итог
- **THEN** запись не выполняется, статус задачи определяет восстановление

### Requirement: Зависшая задача восстанавливается
Задача в `running` с истёкшим lease MUST возвращаться в `queued` и ставиться в очередь заново, если не исчерпан лимит попыток и не запрошена отмена. Задача в `queued` без живой задачи в очереди SHALL ставиться заново; живая задача в очереди SHALL NOT дублироваться. Задача с действующим lease восстановлением не трогается.

#### Scenario: Воркер упал во время работы
- **WHEN** воркер упал, и lease его задачи истёк
- **THEN** задача возвращается в `queued` и выполняется заново

#### Scenario: Lease ещё действует
- **WHEN** задача в `running` с непросроченным lease
- **THEN** восстановление её не меняет

#### Scenario: Задача ещё стоит в очереди RQ
- **WHEN** задача в `queued`, и соответствующая задача RQ ещё в очереди или выполняется
- **THEN** восстановление не ставит её повторно

### Requirement: Лимит попыток останавливает повторы
Задача, исчерпавшая лимит попыток, MUST при восстановлении получать терминальный статус ошибки (`failed` для прогона и HH sync, `error` для LLM-задачи) с сообщением о превышении попыток, а не уходить на повтор. Лимиты: `PARSE_JOB_MAX_ATTEMPTS` (3), `LLM_JOB_MAX_ATTEMPTS` (2), `HH_SYNC_JOB_MAX_ATTEMPTS` (2).

#### Scenario: Прогон падает раз за разом
- **WHEN** прогон трижды захватывался воркером и каждый раз терял lease
- **THEN** прогон получает `failed` с сообщением «Превышено число попыток (3)» и не занимает слот активного прогона

### Requirement: Отмена хранится флагом в БД
Отмена MUST запрашиваться флагом `cancel_requested` в строке задачи и действовать после рестарта API и воркера. Задача в `queued` SHALL сразу получать `cancelled`; задачу в `running` останавливает воркер в своей точке проверки. Зависшая задача с запрошенной отменой SHALL при восстановлении получать `cancelled`, даже если исчерпан лимит попыток.

#### Scenario: Отмена задачи в очереди
- **WHEN** запрошена отмена задачи в `queued`
- **THEN** задача сразу получает `cancelled` и не выполняется

#### Scenario: Отмена побеждает лимит попыток
- **WHEN** для выполняемой задачи запрошена отмена, а затем воркер пропал, и попытки исчерпаны
- **THEN** при восстановлении задача получает `cancelled`, а не `failed` / `error`

### Requirement: Единственность активной задачи
Активным MUST быть не больше одного прогона парсинга и не больше одного HH sync одновременно; повторный запуск SHALL получать 409 `CONFLICT_ACTIVE_RUN`. Для LLM-оценки и письма активной MUST быть не больше одной задачи на пару пользователь–вид–резюме–вакансия: повторный запрос SHALL возвращать уже активную задачу. Ограничение MUST держаться и при параллельных запросах.

#### Scenario: Второй прогон, пока идёт первый
- **WHEN** прогон в `queued` или `running`, и администратор запускает ещё один
- **THEN** ответ 409 с кодом `CONFLICT_ACTIVE_RUN`, второй прогон не создаётся

#### Scenario: Повторный запрос оценки пары
- **WHEN** задача оценки пары ещё выполняется, и пользователь снова запрашивает оценку той же пары
- **THEN** ответ 202 с тем же `job_id`, новой задачи нет

#### Scenario: Параллельные запросы одной пары
- **WHEN** несколько запросов одной пары приходят одновременно
- **THEN** создаётся одна задача

### Requirement: Лимит параллельных LLM-задач пользователя
Пользователь MUST иметь не больше `ai.interactive_per_user_limit` активных LLM-задач; запрос сверх лимита SHALL получать 429 `RATE_LIMITED` (retryable) без создания задачи. Лимит MUST соблюдаться при параллельных запросах.

#### Scenario: Лимит исчерпан
- **WHEN** у пользователя уже столько активных LLM-задач, сколько разрешает лимит, и он запрашивает оценку другой пары
- **THEN** ответ 429 `RATE_LIMITED`, новая задача не создаётся

### Requirement: Идемпотентная постановка
Запуск прогона, HH sync и ручного импорта MUST принимать `Idempotency-Key`; ключ принадлежит пользователю, у разных пользователей одинаковые ключи не пересекаются. Повтор с тем же ключом и телом SHALL возвращать сохранённый ответ без новой задачи; пока первый запрос выполняется — 409 `IDEMPOTENCY_IN_PROGRESS` (retryable); тот же ключ с другим телом — 409. Ключ, чей запрос завершился ошибкой, SHALL освобождаться. Ключ длиннее 128 символов — 400.

#### Scenario: Повтор после успеха
- **WHEN** администратор повторяет запуск прогона с тем же `Idempotency-Key`, и первый запрос уже завершился
- **THEN** ответ — тот же `run_id`, нового прогона нет

#### Scenario: Первый запрос завершился ошибкой
- **WHEN** запрос с ключом получил 409 `CONFLICT_ACTIVE_RUN`, и его повторяют с тем же ключом
- **THEN** повтор снова выполняется и снова получает 409 `CONFLICT_ACTIVE_RUN`, лишней задачи не создаётся

#### Scenario: Тот же ключ, другое тело
- **WHEN** ключ уже использован с одним телом, и приходит запрос с тем же ключом и другим телом
- **THEN** ответ 409, задача не создаётся

#### Scenario: Тот же ключ у другого администратора
- **WHEN** администратор A запустил прогон с ключом `k1`, прогон завершился, и администратор B запускает прогон с ключом `k1`
- **THEN** запрос B выполняется сам: создаётся новый прогон, ответ A ему не возвращается

### Requirement: Режимы rq и inprocess взаимозаменяемы
Каждый тип задачи MUST выполняться одинаково в режиме `rq` (очередь Redis, отдельный воркер) и `inprocess` (поток в процессе API). В `inprocess` восстановление MUST работать в процессе API и при его старте сразу ставить заново оставшиеся `queued`; в `rq` восстановление живёт в воркерах, и старт API его SHALL NOT запускать.

#### Scenario: Старт API в inprocess
- **WHEN** API стартует в `inprocess`, а в БД остался прогон в `queued` от прошлого процесса
- **THEN** прогон ставится в работу без ожидания порога «зависшей» задачи

#### Scenario: Старт API в rq
- **WHEN** API стартует с бэкендами `rq`
- **THEN** API не восстанавливает задачи сам
