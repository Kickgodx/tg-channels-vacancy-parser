# Описание `config.yaml`

Структура соответствует `tg_jobs_parser/config/schema.py`.

---

## `telegram` — доступ к каналам

Сообщения читаются **только через Telethon** (MTProto, ваш аккаунт). Нужны `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` в `.env` и один раз — авторизация в консоли (создаётся файл сессии).

| Поле | Назначение |
|------|------------|
| **`telethon_session_file`** | Путь к файлу сессии Telethon после первой авторизации. |

|------|------------|
| **`channels`** | Список каналов: username **без** `@` (например `qa_jobs`). С них по очереди тянутся посты. |

## `search` — временной охват выборки

| Поле | Назначение |
|------|------------|
| **`date_from`** / **`date_to`** | Границы дат сообщений (строки, парсятся при каждом запуске). `date_from`: ISO или `week_ago` / `week` / `today-7d` / `неделя` → сегодня − 7 дней; пусто — без нижней границы. `date_to`: ISO или `today` / `сегодня` / пусто → сегодня. Telethon идёт по истории, пока не выйдет за диапазон или лимит `max_posts_per_channel`. |
| **`max_days`** | Запасной/ограничивающий горизонт дней для поисковой конфигурации (в схеме не более 365). |

## `filters` — что оставить в выдаче после парсинга

| Поле | Назначение |
|------|------------|
| **`specializations`** | Список **имён** профилей из словаря (в т.ч. из `DEFAULT_SPECIALIZATIONS` в коде + `dictionaries.specializations`). Пост остаётся, если хотя бы одна из указанных специализаций **распознана** в тексте. Если список **пустой** — ограничения по этому фильтру нет. |
| **`exclude_keywords`** | Подстроки/слова в тексте: если совпало — пост **выбрасывается**. Объединяется с исключениями из словаря (см. `dictionaries.exclude_keywords`). |
| **`countries`** / **`cities`** | Непустые списки включают фильтр по стране/городу (поля из текста или из экстракторов). **Пустой список** = «не фильтровать». |
| **`work_formats`** | Политика по формату работы (`remote`, `hybrid`, `office`, `relocation`), либо `any` = не фильтровать, либо `exclude_office` без других ограничений — отсечь явный офис при необходимости. |

## `parser` — порог «это похоже на вакансию», лимиты и дедуп

| Поле | Назначение |
|------|------------|
| **`progress_batch_posts`** | Как часто отдавать снимок прогресса в UI (каждые N постов). |
| **`db_flush_every_posts`** | Промежуточная запись в БД (только backend-прогоны): сливать накопленные уникальные вакансии каждые N обработанных постов или при накоплении `db_flush_pending_vacancies` — что наступит раньше. При падении прогона уже записанные батчи не теряются. |
| **`db_flush_pending_vacancies`** | Порог по числу ещё не записанных уникальных вакансий для промежуточного слива в БД (работает в паре с `db_flush_every_posts`). |
| **`vacancy_score_threshold`** | Минимальный суммарный **vacancy_score** правил из `extraction/vacancy_detector.py` (вакансия, разработчик, зарплата, грейд, компания, контакт, офис/hybrid и т.д.). Ниже — пост не считается кандидатом. |
| **`vacancy_min_substantive_score`** | Минимум счёта **без бонуса за email/`@`** — чтобы не заходили посты только с упоминанием контакта. |
| **`max_posts_per_channel`** | При заданных датах — максимум сообщений, которые можно **просмотреть** от новых к старым, пока не выйдешь за `date_from` или лимит. |
| **`channel_concurrency`** | Сколько каналов опрашивать **одновременно** в рамках одной Telethon-сессии. `1` — старое последовательное поведение, `3..8` — разумный диапазон. Слишком большое значение повышает риск `FloodWait` от Telegram. Это же размер очереди между вычиткой и разбором: прочитанные каналы сразу уходят в обработку, а если она отстаёт, вычитка ждёт. |
| **`incremental_fetch`** | `true` (по умолчанию) — backend-прогон читает из канала только сообщения **новее чекпоинта**. Чекпоинт канала записывается, как только его посты разобраны и сохранены, ещё до конца прогона. Чекпоинт канала — «прочитано всё с даты X по сообщение N»; используется, если окно прогона заканчивается сегодня и `date_from` не раньше X. Иначе (новый канал, окно расширено назад, `date_to` в прошлом) — канал читается целиком. Чекпоинт не двигается, если канал прочитан не до конца (лимит, FloodWait, ошибка, отмена) или в режиме `ai.mode: primary` часть постов не разобрал LLM. Разовый полный перечит — галочка в форме запуска (`parser.incremental_fetch: false` в теле `POST /runs`). |
| **`flood_wait_max_seconds`** | FloodWait от Telegram до N секунд (по умолчанию 300) пережидается, и обход канала продолжается с места остановки (до 3 раз на канал); дольше — канал возвращается с уже прочитанными постами и предупреждением, а не пустым. Короткие ожидания (до 60 с) Telethon выполняет сам. |
| **`sleep_between_requests_seconds`** | Минимальный интервал (с) между запросами страниц истории канала — 100 сообщений на `GetHistoryRequest`; время самого запроса и разбора страницы в него входит. `1` (по умолчанию) — тот же темп, что встроенный `wait_time` Telethon при больших обходах; `0` — без пауз (быстрее, но выше риск `FloodWait`). Интервал действует внутри канала; каналы читаются параллельно (`channel_concurrency`), так что общий темп ≈ `channel_concurrency / интервал` страниц в секунду. Поднимать, если часто ловите `FloodWait`. Цена паузы видна в логе канала («паузы между страницами: N с»), в атрибуте span `telegram.pause_seconds` и в метрике `telegram_request_pause_seconds_total` (доля во времени обхода — `rate(telegram_request_pause_seconds_total) / rate(telegram_channel_fetch_duration_seconds_sum)`). |
| **`vacancy_fuzzy_duplicate_threshold`** | Порог **0–100** для RapidFuzz: при сравнении составного «ключа» вакансии с уже известными группами; выше порога — считают дубликатом той же группы. |
| **`fuzzy_compare_prefix_len`** | Сколько **первых символов** очищенного текста попадают в этот ключ для fuzzy‑дедупа (наряду с компанией, зарплатой, спеками и т.д.). |
| **`fuzzy_dedup_block_by_specializations`** | `true` (по умолчанию) — fuzzy‑дедуп сравнивает вакансию только с группами с **тем же набором специализаций**. Без этого каждая вакансия сравнивается со всеми группами прогона (O(N²), ~10 мкс на пару — минуты на десятках тысяч). Цена: почти‑дубли, у которых извлеклись разные специализации, fuzzy не склеит; точные дубли (по хэшу текста) ловятся всегда. `false` — прежнее сравнение со всеми группами. |

## `dictionaries` — расширение встроенных словарей

| Поле | Назначение |
|------|------------|
| **`specializations`** | Дополнительные **синонимы** к уже заданным в коде ключам типа `"Python"` → добавляются фразы, по которым матчится эта специализация. |
| **`exclude_keywords`** | `null` — к **дефолтному** большому списку из схемы (`DEFAULT_EXCLUDE_KEYWORDS`) добавляются только `filters.exclude_keywords`. Если задать **список** — **только он** считается базой исключений (дефолт из кода подменяется). |
| **`technologies`** | Дополнительные технологии к `DEFAULT_TECHNOLOGIES`, для распознавания в тексте поста. |
| **`work_format_synonyms`** | Дополнительные фразы к встроенным синонимам remote/hybrid/office/relocation для детектирования формата работы. |

## `ai` — OpenRouter (опционально)

Подробнее — раздел AI в [README](README.md). Кратко по версиям промпта:

| Поле | Назначение |
|------|------------|
| **`prompt_version`** | Должен совпадать с `EXTRACT_PROMPT_VERSION` в `tg_jobs_parser/ai/prompts.py`. Кэш LLM ключуется константой; при расхождении — warning. Смысловое изменение extraction-промпта → bump константы. |
| **`concurrency`** | Параллелизм LLM при **парсинге** постов. |
| **`interactive_concurrency`** | Inprocess: размер ThreadPool; при RQ — ориентир для `--scale llm-worker`. |
| **`interactive_per_user_limit`** | Сколько LLM-джоб (`queued`+`running`) одновременно на одного пользователя (по умолчанию 2); сверх лимита — HTTP 429. |
| **`requests_per_minute`** | Темп запросов к OpenRouter. При заданном `REDIS_URL` — **общий** на все процессы (API, parse-worker, реплики llm-worker): счётчик минутного окна в Redis; внутри процесса запросы дополнительно разносятся равномерно. Без Redis (или при его сбое) — лимит каждого процесса отдельно. |
| **`interactive_daily_request_budget`** | Суточный (UTC) бюджет запросов к провайдеру для пользовательского LLM — мэтчинг и сопроводительные письма всех пользователей вместе; повторы после ошибок тоже считаются. Счётчик общий в Redis, без Redis — на процесс. Исчерпан — мэтчинг и письма завершаются ошибкой до полуночи UTC, затем LLM снова доступен без рестарта. Парсинг (доступен только админу) бюджетом не ограничен. `0` (по умолчанию) — без бюджета. |
| **`max_retries_on_error`** | Сколько раз повторить вызов при транзиентном сбое: 5xx, 408/409, таймаут, обрыв соединения (по умолчанию 2, `0` — без повторов). Пауза 2/4/8… с, не дольше 30 с. Отдельно от `max_retries_on_429`. |
| **`circuit_breaker_errors`** | Circuit breaker прогона: после стольких постов подряд с ошибкой LLM (уже после повторов и fallback-моделей) LLM отключается до конца прогона — как при исчерпанной квоте (по умолчанию 5, `0` — выключен). При полном отказе провайдера остальные посты не ждут повторов и таймаутов. |
| **`max_error_ratio`** | Только `mode: primary`: доля LLM-запросов с ошибкой, выше которой прогон считается неполным — статус `partial` (по умолчанию `0.1`, `1` — не проверять). Посты с ошибкой в `primary` отброшены, чекпоинты каналов с первой такой ошибки не двигаются. |
| **`mode`** | `assist` — при отключении LLM (лимит или circuit breaker) остаток постов разбирается rules. `primary` — остаток не разбирается, прогон завершается `partial` с причиной в `error_message` (собранные вакансии сохраняются). |

Env (не yaml): `LLM_JOB_BACKEND=inprocess|rq`, `REDIS_URL`, `LLM_WORKER_METRICS_PORT`, `LLM_JOB_STUCK_MINUTES`, `LLM_JOB_LEASE_SECONDS`, `LLM_RQ_JOB_TIMEOUT_SECONDS`, `LLM_JOB_MAX_ATTEMPTS`, `JOB_RECOVER_INTERVAL_SECONDS` — см. `.env.example`.

Прогоны парсинга (не yaml): `PARSE_JOB_BACKEND=inprocess|rq`, `PARSE_JOB_STUCK_MINUTES`, `PARSE_JOB_LEASE_SECONDS`, `PARSE_JOB_MAX_ATTEMPTS`, `PARSE_RQ_JOB_TIMEOUT_SECONDS`, `PARSE_WORKER_METRICS_PORT` — в Docker Compose по умолчанию `rq` + сервис `parse-worker`; см. `.env.example` и README.

HH sync (не yaml): `HH_SYNC_JOB_BACKEND=inprocess|rq`, `HH_SYNC_JOB_STUCK_MINUTES`, `HH_SYNC_JOB_LEASE_SECONDS`, `HH_SYNC_JOB_MAX_ATTEMPTS`, `HH_SYNC_RQ_JOB_TIMEOUT_SECONDS`, `HH_WORKER_METRICS_PORT` — в Docker Compose `rq` + сервис `hh-worker`.

Liveness RQ-воркеров (не yaml): `WORKER_HEARTBEAT_MAX_AGE_SECONDS` (порог healthcheck, 180 с), `WORKER_STALL_EXIT_SECONDS` (watchdog завершает зависший воркер, 900 с; `0` — выключен).

**Идемпотентность мутаций:** заголовок `Idempotency-Key` на `POST /runs`, `POST /hh/sync`, `POST /vacancies/import` (TTL 24ч). Повтор с тем же ключом возвращает сохранённый ответ.

**Ошибки API:** `detail` может быть объектом `{code, message, retryable}` (например `CONFLICT_ACTIVE_RUN`).

**Overrides прогона:** `POST /runs` принимает только whitelist полей (каналы, даты, фильтры, пороги score, `ai.enabled|model|fallback_models|use_cache`); остальное — включая `ai.base_url`, лимиты и `telegram.telethon_session_file` — меняется только в этом файле. Неизвестное поле → 422.

**Frontend при `API_KEY`:** задайте `VITE_API_KEY` (тот же секрет) — UI шлёт его заголовком `X-API-Key`; SSE ключ не нужен — он проверяется при выдаче тикета (`POST /auth/sse-ticket`). Ключ попадает в JS-бандл, поэтому это дополнительный слой поверх JWT, а не защита сам по себе.

## `retention` — TTL хранения вакансий и служебных данных

| Поле | Назначение |
|------|------------|
| **`vacancy_ttl_days`** | Через сколько дней архивировать вакансию (soft delete, `archived_at`): по `post_date`, а если его нет — по `parsed_at`. `0` — не архивировать. Проверка идёт при старте backend, раз в час фоном и после каждого прогона. Повторная публикация того же текста сдвигает `post_date` вперёд и возвращает вакансию из архива. |
| **`parse_runs_ttl_days`** | Через сколько дней после завершения удалять прогон (`parse_runs`: снимок конфигурации, `run_params`, метрики). Вакансии прогона остаются в корпусе. По умолчанию 180; `0` — хранить всегда. |
| **`llm_jobs_ttl_days`** | Через сколько дней удалять завершённые LLM-джобы (`done` / `error`). Сами оценки и письма лежат в `vacancy_matches` / `cover_letters` и не удаляются. По умолчанию 30; `0` — хранить всегда. |
| **`exchange_rates_ttl_days`** | Через сколько дней удалять курсы валют (`exchange_rates`, по `rate_date`). Пересчёт зарплат в ₽ берёт только последнюю дату, поэтому история не нужна. Последняя дата остаётся всегда (даже если ЦБ долго недоступен); курсы из окна `fx.sync_days_on_startup` тоже не удаляются, иначе каждый старт заново качал бы их из ЦБ. По умолчанию 60; `0` — хранить всегда. |

Очистка идёт в фоне backend при старте и раз в час, вместе с архивацией вакансий: кроме TTL выше, удаляются просроченные записи кэша LLM (`ai.cache_ttl_days`, по умолчанию 45 — чуть больше `vacancy_ttl_days`), записи кэша от прежних версий промпта (после bump `EXTRACT_PROMPT_VERSION` они уже не читаются) и ключи идемпотентности. Удаление — пачками, короткими транзакциями.

## `hh` — парсинг HH.ru (admin sync)

Секреты (`HH_API_TOKEN`, `HH_CONTACT_EMAIL`) задаются в `.env` / переменных
контейнера, не в yaml.

| Поле | Назначение |
|------|------------|
| **`enabled`** | Разрешить `POST /hh/sync` и вкладку `/hh`. |
| **`listing_ttl_days`** | TTL кэша короткой выдачи `hh_listings` (по `last_seen_at`). `0` — не чистить. После purge detail снова запросится. |
| **`max_rps`** | Лимит RPS к HH API (retry на 429). |
| **`db_flush_batch_size`** | Сколько вакансий копить перед UPSERT+commit (по умолчанию 30). Буфер в памяти очищается после каждого батча. |
| **`api_base` / `host`** | Базовый URL API и query `host`. |
| **`app_name` / `app_version`** | Часть `User-Agent` / `HH-User-Agent`. |
| **`search.text`** | Текст поиска (дефолт — AQA/Python как в MVP hhparser). |
| **`search.professional_role`** | Роли HH (124 = тестировщик, 96 = разработчик). Имена ролей попадают в `detected_specializations` и дублируются в `QA` / `Software Engineer`; оба набора есть в `DEFAULT_SPECIALIZATIONS` для фильтров UI. |
| **`search.per_page`** | Размер страницы (макс. 100). |

## `output` — куда писать файлы

| Поле | Назначение |
|------|------------|
| **`directory`** | Каталог вывода (`partial_*.json` при `save_progress_batches`). |
